# J0.3.1 — Deterministic tool policy boundaries

Historical increment. The generalized authenticated J0.3 path now uses
[durable authorization](j0.3-authorization.md); statements below about absent
generic approvals/controls describe J0.3.1 only. The legacy synthetic read retains
its policy and now also checks the persisted J0.3 emergency state.

This is the first bounded J0.3 implementation, not J0.3 COMPLETE or Foundation v1 GO.

## Active path

The web backend authenticates its API request with an HMAC service proof. Identity
checks the live capability, parent owner/session/device/epoch, exact scope/resource,
one-use challenge and recipient signature. Only then does the API construct a v2
context. The recipient receives A1 for its own proof, never the owner's A2/A3.
Expiry is capped by capability, parent session absolute/idle expiry and device expiry.
Suspicious posture is blocked; unknown posture is not claimed to be healthy or attested.

The registered tool gateway loads `config/policy.development.json` beside the active
development config at startup. There is no HTTP endpoint to install tools or replace
this document. Invalid schema/version/extra fields/duplicate rule IDs abort startup.
The sole registered tool is `mock.repository.read` on `repository-x`, scope `mock.read`.
Subjects may have a legitimate capability for a different resource and still be denied
by policy. Authenticated does not mean authorized.

Request input, validated input, context, descriptor and policy are copied/frozen;
only JSON up to 100,000 bytes is accepted by the gateway. HTTP is additionally
limited to 64 KiB. The policy engine is synchronous and does not call models/network.

## Policy invariants

- Default deny; exact actor kind/optional IDs, scope, tool, resource, mode and permission.
- An explicit matching deny wins regardless of rule order. All matching allow
  restrictions combine: highest assurance and any required approval remain required.
- Actor environment and owner binding must match authenticated authority. Non-development
  execution, A0/A4, unknown/temporary/revoked/hardware-root trust are denied here.
- Observe/suggest/prepare/write imply minimum P0/P1/P2/P3. Private/secret data or low
  physical effects imply P4. Underclassified descriptors fail rather than being upgraded
  silently. Destructive, security/credential changes, financial operations and high
  physical effects are critical and unconditionally denied, as is P5.
- P4 requires fresh A3 (at most 60 seconds), privileged device and explicit approval.
  The active delegated runtime cannot produce this context or a generic tool approval.
- External actions are disabled in every mode; no policy rule can override this.

| Mode / control | Implemented policy behavior |
| --- | --- |
| Safe | Only P0 observe |
| Assistant / Guest | At most P1; guest only synthetic/public data |
| Copilot / Private / Focus | P2+ needs approval; focus additionally requires exact focus resource |
| Autonomous | Explicitly allowed low-risk P0–P3 may be preapproved; P4 still needs approval |
| Emergency / Frozen / Shutdown | Deny all tool invocations |
| Paused | Deny non-owner tool work; owner still needs every other check |
| Disconnected | Covered by unconditional external-action denial in this increment |

Only fixed Safe mode is wired into the current runtime. Other modes and changing
control states are exercised with synthetic test fixtures, not exposed management APIs.

## Approvals and execution races

Approval consume contract v2 binds owner, recipient actor, issuing device and session,
environment, request, tool descriptor hash, exact resource, canonical input hash,
policy revision/hash and entire control-state hash/epoch. A real adapter must verify
fresh owner authorization and atomically consume an unexpired proof once. The active
runtime adapter denies every proof; no generic approval is issued or trusted yet.
Identity-admin approvals from J0.2 are separate and remain durable/implemented.

The gateway audits requested and authorized before execution and checks controls,
abort and authority expiry after each asynchronous gate. It checks again after
execution and before returning a result. Any changed control snapshot forces denial.
Policy is immutable for the life of the gateway; replace the instance on a future
authorized policy change. Its digest invalidates old approval bindings.

The current identity transaction serializes the synthetic action with revocation.
Do not keep future slow external operations inside that transaction. They need a
transactional dispatch/outbox, revocation fencing, idempotency and reconciliation.
An AbortSignal is cooperative. None of this terminates an uncooperative process,
undoes a completed effect or establishes an independent emergency controller.

## Audit / migration / privacy

v1 audit stays in `audit.entries`; v2 goes to `audit.policy_entries`. Migration 0003
only adds the new table and append-only triggers, with PUBLIC privileges revoked.
The migrator grants runtime SELECT/INSERT only. The existing transaction/advisory lock
and five-second lock timeout remain. No production database was changed. Large-install
upgrade timing and backup validation remain untested; development fresh-install and
idempotent migration are the intended acceptance scope.

v2 records include request ID, actor, tool, declared permission, derived risk, matched
rules, policy digest/revision, control epoch, outcome/reason and input/resource hashes.
Raw arguments, capability/session tokens, signatures, provider keys and outputs are
not recorded. Plain hashes do not hide low-entropy values; do not pass real secrets as
arguments. Policy audit is stored but not yet displayed in the identity console.

Pre-execution audit failure blocks the tool. Post-effect audit failure yields no
successful response and no automatic retry; callers must treat it as uncertain.
PostgreSQL triggers/roles are append-only controls, not independent immutability.
Administrators able to disable protections remain outside that guarantee.

## Still open for J0.3

Owner-authenticated durable generic approval issuance, review/cancellation UI,
protected policy change ceremony, signed distribution/rollback protection,
independent emergency command channel and persisted controls, worker isolation and
termination, connector reconciliation, authenticated audit inspection and security
review. No real/private-data/financial/device operation is enabled by this increment.
