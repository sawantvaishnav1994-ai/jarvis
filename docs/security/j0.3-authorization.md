# J0.3 authorization — development boundary

## Trust and identity

Models have no security authority. Existing J0.2 owner actions require device
proof and passkey step-up for security commands. A separate recipient key signs
one-use, exact-command challenges for restricted subjects. HTTP never accepts
a caller-supplied owner/assurance context. Root ownership and passkey ceremonies
are unchanged. Every action rechecks the current owner epoch, subject, delegated
parent session/device, expiry and revocation.

Security commands are composed into IdentityEngine by the API, not registered by
agents. Package classes are trusted application code, not a sandbox for arbitrary
JavaScript with database credentials. No plugin upload/execution endpoint exists.

## Authority and policy

Strict versioned schemas cover capabilities, exact resource scopes, permission,
policy/decision, contextual risk, approvals, delegations, controls, budgets and
authorizations. Unknown commands, capabilities, versions, states and input fields
fail closed. Resource IDs are exact; arbitrary filesystem glob access is not enabled.

Policies are owner-created drafts with monotonic revisions and verified activation.
Prior active versions become superseded. Disabled/superseded versions cannot be
reactivated. Constitution is protected code: no administrative policy can replace
it. Denials at any matched level win, with highest-level denial explained first.
A policy change/control epoch invalidates outstanding approvals and authorizations.

Risk derives from registered tool simulation and validated context, including
permission, reversibility, blast radius, amount, privacy/security/physical impact,
production, volume/resource count, trust/assurance, novelty/anomaly, confidence,
verification and zones. Synthetic test flags are not evidence for a real deployment.
Real adapters must supply authenticated verification artifacts before being enabled.

R3 approval and R4 approval plus step-up are constitutional floors; owner risk rules
may tighten them. R5/P5 and Z5 execution stay prohibited because hardware A4 and
critical owner ceremonies are not established. All allowed outcomes are audited,
including AUTO_ALLOW. Financial policy and field-scope contracts exist, but no
financial connector is installed. Field scopes can only restrict, never grant.

## Durable approval and execution

Pending approval includes readable action, requester, target, changes/input digest,
risk/reasons, reversibility, impact, capability, zone, A3 requirement and expiry.
The console shows the exact request and Approve/Deny controls. Approval decisions
are bound by J0.2 WebAuthn evidence to approval ID, full request hash and decision.
The requester cannot approve. Evidence is retained in encrypted append-only audit.

One-time authorization binds actor, owner/session/device, request/tool/capability,
resource/environment, exact input hash, approval, policy versions/hash, risk/zone,
owner/control epochs and expiry. Client objects must exactly equal the stored
record. Every consume rechecks live authority, policy, budget and controls.
A private one-shot in-process permit additionally protects the concrete handler
from copied/fabricated authorization objects. There is no public permit mint API.

Delegation extends J0.2 identity.delegations rather than introducing another identity
system. Development grants have bounded TTL, uses, maximum risk and optional tool.
Production proposals require an explicit owner review rule and a live scoped
development grant for the same resource. The approved exception is exact and
one-use; it does not silently add production to agent permissions.

## Emergency state and persistence

Six deterministic global flags and actor freeze state persist encrypted in
security.governance_state. The existing identity advisory lock and transaction
serialize administration, approval, revocation and consumption with append-only
audit.identity_events. The old J0.2 synthetic read also checks these controls.
Owner release requires the same signed fresh passkey ceremony as activation.
Freezing an actor revokes its delegations and creates an incident record for owner
inspection. Operational health/queue pings are not powerful agent operations.

This is policy-level emergency enforcement, not an OS network firewall. Existing
host stop scripts remain unchanged. Full hostile-worker termination remains open.
Only synchronous deterministic mocks execute inside this bounded transaction;
never add slow network or untrusted handlers here. Real effects require a durable
dispatch/outbox, revocation fences, idempotency and uncertain-outcome reconciliation.
A database commit failure cannot undo an external effect; none is enabled here.

The encrypted governance aggregate contains policies/versions/bindings, requests,
risk/evaluations, approvals/decisions, authorizations, budgets and global states.
Capabilities/resources/zones are strict contracts; delegation lives in existing
identity tables; incidents/evidence live in existing audit. This deliberately avoids
duplicating identity or creating empty tables for every conceptual entity.
Per-record repositories/partitioning can follow scale without changing contracts.

Migration 0004 is additive and checksummed. Runtime gets SELECT/INSERT/UPDATE only,
not DELETE, on governance state. Existing applied migrations/audit constraints are
unchanged. Rollback keeps the additive table; no destructive down migration exists.
A raw database dump retains encrypted security/private payloads. Host/root access
and a database administrator disabling protections remain outside the guarantee.

Audit is append-only under runtime privileges/triggers, **not independently
immutable storage**. Independent archives, multi-node anti-rollback/replication,
hardware key custody, bounded storage maintenance and complete disaster recovery
remain production limitations. No live owner data or keys are provisioned by tests.
