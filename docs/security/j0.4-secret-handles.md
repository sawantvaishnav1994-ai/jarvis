# J0.4 governed synthetic credential use

The existing J0.3 constitution still denies raw Z5/R5/P5 execution. There is no
raw-secret endpoint, arbitrary resolver, dynamic handler or credential export.

`data.secret.use` is a P4/Z4 **tool-use authorization**, not permission to read D5.
It requires `secrets.handle.use`, exact `owner-data` scope, development environment,
fresh A3 owner approval, bounded delegation/budget and J0.3's one-use permit.
The approved transient input is hash-bound to the request and contains only the
provider-independent handle `secret://synthetic/credential-check` and the closed
tool identifier `synthetic.credential-check`. Other handles are denied. D5-labeled
generic data requests remain denied rather than downgraded.

Inside the same authenticated transaction, the trusted executor maps that handle
to `development/tools/synthetic-credential`. Existing development setup adds a
random, separately scoped encrypted vault record without replacing any key or
credential. FileSecretManager validates the fixed service identity and reference;
the requesting agent never becomes the vault actor. The synthetic tool performs
an internal keyed operation and destroys both its temporary proof and lease buffer.
Only a strict fixed receipt returns: version, tool, verified, secretReturned=false.
No plaintext, digest/MAC, arbitrary output, callback or caller-supplied program is
returned or executed. The audit contains authorization/policy/request metadata,
not transient secret material. Vault errors are sanitized.

This is development acceptance of mediated use, not a real connector, vault
administration UI, HSM custody or hostile-process isolation. Trusted host code and
the OS account remain in the trusted computing base; JavaScript memory erasure
cannot be guaranteed for all copies. Future connectors require separately reviewed
fixed handle/tool bindings and output contracts, not expansion of this probe into
a general secret-reading operation. The ordinary J0.3 raw-secret denial is unchanged.
