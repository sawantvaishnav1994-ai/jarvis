# Recovery deletion obligations and shared attachments

Migration 0007 is additive. Migrations 0001–0006 remain byte-for-byte unchanged.
New backups have an explicit, immutable development retention deadline (30 days).
Old snapshots lacking that evidence fail closed; they are not silently assigned
unlimited retention. The runtime cannot update/delete retention or obligation rows.

Within the same identity-authorized deletion transaction, every older owner backup
receives minimal record/deletion IDs and purge-eligibility timestamps. Normal
validation/restore rejects such snapshots immediately. Expired snapshots likewise
cannot restore. Current tombstone comparison remains an independent restore guard.
The conservative rule invalidates an entire older snapshot rather than attempting
to edit encrypted artifacts in place. Post-deletion backups contain tombstones and
exclude deleted active content. Backup index/lifecycle metadata stays with the
separate recovery store; operational snapshots do not recursively contain backups.

Eligibility is not physical erasure. This phase does not assert that a scheduled
off-host/immutable provider purge has occurred. Time-injected tests verify expiry
without pretending that 30 real days elapsed. Independent protected backup deletion
and production retention administration remain separate hardening work.

Attachment links use canonical owner/object IDs and database foreign keys, never
caller-supplied reference counts. Deleting one attachment unlinks its reference;
an object with another legitimate reference stays readable. The final reference
permits the existing staged revocation and separately authorized physical purge.
The purge rechecks ownership, class, linkage and active references. Legacy missing
links block deletion until exact A3 owner-approved reconciliation reads the encrypted
canonical attachment, verifies its message lineage and owner-scoped object, and
adds only the missing link. A conflicting link is rejected, not overwritten.
