# J0.1 security boundaries

Historical J0.1 scope. The active J0.2 identity changes are documented in
[J0.2 boundaries](j0.2-identity.md); statements below about disabled owner/device
enrollment describe the earlier milestone, not the current identity console.

J0.1 is a local engineering platform using synthetic data. Runtime actors are
internal service identities. Owner objects in tests are fixtures, not evidence
of authentication. J0.2 must implement owner enrollment, session authentication,
cryptographic device trust, recovery and trusted execution-context construction
before exposing Core, memory or tools over HTTP. An object that says `kind: owner`
is not an authentication credential.

- API, web, worker, PostgreSQL and Redis bind to loopback.
- Invalid/unknown security settings abort startup. Cloud models, agents, powerful
  tools, device enrollment and personal-data endpoints are disabled.
- P0–P5 are explicit. The foundation policy requires a development owner and
  exact scope; it denies sensitive/critical actions. P1–P3 also need an approval
  authority. Approval storage/authentication is a port reserved for J0.2/J0.3.
- Tools validate arguments, audit requests before policy evaluation, check risk,
  consume exact-bound approvals, execute, verify and audit outcomes. Audit
  failure before execution prevents action. Post-action audit failure means the
  caller cannot treat the operation as cleanly complete; future real connectors
  require idempotency, uncertain-outcome reconciliation and external witnesses.
- Secret files are encrypted with AES-256-GCM. A separate 0600 master-key file
  sits outside the project/vault directory. Private directories use 0700.
  Services lease only configured references; agents cannot lease permanent
  credentials. Lease buffers are cleared on release/expiry, but JavaScript string
  copies and database clients cannot promise complete process-memory erasure.
- This vault protects files at rest; it is not a hardware enclave. Host root or
  the same OS account can read running-process credentials. Docker sees the
  development passwords in container environment configuration. Never publish
  that configuration or use production credentials here.
- Memory and event payloads are encrypted. Operational logs use reviewed event
  labels and metadata only. Audit stores an argument digest, not raw arguments;
  low-entropy arguments can still be guessed from an unkeyed digest. Do not use
  secrets as tool arguments. J0.3 must define redaction/opaque bindings per tool.
- Audit table DML privileges and triggers prevent normal updates/deletes/truncate.
  The database administrator can still disable/drop these protections. This is
  append-only access control, **not independently immutable audit storage**.
- J0.1 has no durable owner-authenticated export/delete/restore API. Memory
  adapters support scoped deletion; complete data sovereignty belongs to J0.10.

Threats requiring later gates include authenticated remote transport, malicious
local users, prompt injection in retrieved material, approval replay persistence,
policy administration, device private-key custody, lost keys, OS containment,
independent audit witnesses and disaster recovery. The preserved Python reference
has useful implementations/tests for several of these; they are not automatically
present in the new TypeScript runtime.
