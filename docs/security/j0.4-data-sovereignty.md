## Increment A: classified contracts and envelope encryption

Implemented as additive, testable libraries. No private-data HTTP endpoint or new
live database schema is enabled. Existing v1 memory/ciphertext readers stay unchanged.

| Classification | Meaning | New foundation behavior |
| --- | --- | --- |
| D0 | Public | Explicit classification; encrypted by the envelope primitive too |
| D1 | Internal | Encrypted payload; no implicit external-AI permission |
| D2 | Private | Encrypted payload; separate consent, retention and destination |
| D3 | Sensitive | Encrypted; cloud-model disclosure vetoed in this increment |
| D4 | Critical | Encrypted; cloud-model disclosure vetoed; future restricted owner policy required |
| D5 | Secret | Ordinary memory/conversation/envelope persistence and model disclosure denied; dedicated vault only |

Classification is an explicit trusted input, not automatic secret detection. A
credential mislabeled D0 is not magically recognized. A D3/D4 label alone does not
implement its authorization rules. Every future storage request must first pass
authenticated J0.3 policy, including service, owner, device and resource scopes.

Retention variants: keep, until a specific timestamp, session-only, never-store.
The durable encryption/record path rejects session-only and never-store inputs;
expired data is denied on encryption, decryption and rewrap. Actual scheduled
deletion, legal hold, replica propagation and backup expiry are not implemented.

Consent independently represents conversation storage, memory creation, project
knowledge, attachment retention, personalization and external AI use. Persisted
conversation consent cannot imply memory consent. These fields describe an owner
decision; they are not signed authorization. The future API must resolve them from
owner-controlled policy, never trust model/client-supplied booleans as authority.

Memory v2 records include subject, source kind/version, capture time, confidence,
verification time, classification, retention, relationships, embeddings references,
derived-source IDs and record version. Conversation v1 records include participants,
messages, author, timestamp, content type, attachment references and optional provider/
model metadata. No provider API object is required to interpret owner data.
Source references are descriptive contracts; cross-owner source resolution, dependency
cycles and full derived-data deletion remain repository responsibilities.

## Cryptography and key boundaries

The new envelope format is explicitly versioned and independent of the existing
RecordCipher format. Each encrypted JSON record gets a fresh random 256-bit DEK.
AES-256-GCM uses 96-bit nonces and 128-bit tags. A versioned KEK encrypts the DEK.
Authenticated bindings cover owner, environment, logical domain, record ID/version
and complete data policy. Wrapped-key authentication additionally binds the KEK ID
and encrypted payload, preventing ciphertext/key mixing.

The format stores scheme, key ID, binding hash, ciphertext/nonces/tags and encrypted
DEK, never the plaintext DEK or KEK. The codec derives the binding from the parsed
record and requires an independently supplied expected owner/record/version/domain/
environment when decoding. The database row itself is not the authority for that
expected reference. Metadata/length and equality leakage are not hidden by encryption.

The development key provider resolves `secret://development/storage/kek/<version>`
inside an already scoped SecretManager. It permits a configured owner-bound storage
service, not an agent, and checks owner/environment/key state. Registries are immutable
snapshots, require exactly one active key and unique IDs/handles. Created/destroyed
keys are unusable; retired keys unwrap only; active keys wrap and unwrap.

Rewrap returns a new envelope with an unchanged data ciphertext and a newly wrapped
DEK. It does not write the database, rotate a live vault, destroy old keys or revoke
old backups. A compromise may require fresh DEKs and full re-encryption: rewrap alone
does not protect old ciphertext already accessible with compromised keys.

Plaintext records are bounded to 48,000 serialized UTF-8 bytes. Large files need a
separate bounded streaming/object format. Leases, DEKs and temporary byte buffers are
cleared where possible; JavaScript strings, GC copies and host-root compromise are
not protected by a memory-erasure claim. Host disk encryption/TPM custody is not
configured or verified. Existing vault master-key custody remains unchanged.

The design uses standard authenticated encryption rather than a new algorithm;
see [OWASP cryptographic storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
and [Node's crypto API](https://nodejs.org/api/crypto.html).

## Privacy veto, not a network permission

`permitsModelDisclosure` is a pure additional check. Cloud disclosure requires
AI-ALLOW, explicit external-AI consent, D0–D2 and exact provider/region allowlists.
D5 never enters a model, including a local one. The helper does not retrieve records,
authenticate users, verify provider residency, redact content, enable network access,
or authorize an action. Retention/consent freshness and minimum-context construction
must precede it. It is not yet wired into the disabled private-data/model path.

## Compatibility and acceptance

Current PostgreSQL domains use `conversations` and `settings`; the owner's conceptual
`conversation` and `system` names do not justify renaming existing schemas. New v2
memory records require explicit classification/provenance/consent migration; missing
legacy fields never default to public or consented. No SQL migration, vault rotation,
production write or owner-data migration was performed in this increment.

The ClassifiedRecordCodec is serialization only. Its JSON round trip is not a full
export, durable backup, transactional repository or disaster restore. It makes no
claims about vector/graph deletion, sync, PITR, independent audit or offline recovery.
Tests use synthetic records and keys. J0.4 GO requires the complete owner's workflow
against real storage and isolated destructive-test copies, not just cryptography tests.
