# J0.5 — Memory Engine, Knowledge Graph & Personal Context

Status: IMPLEMENTATION SPECIFICATION / NOT GO

J1: LOCKED

## 1. Purpose

J0.5 turns the J0.4 owner-controlled data substrate into a trustworthy memory and personal-context system.

Jarvis must not treat every conversation, model output, imported fact or inference as truth. It must decide what may be remembered, preserve source provenance, represent confidence and time, distinguish assertion from inference, detect contradictions, retrieve only relevant memories, respect retention/privacy/external-processing policy, and let the Owner inspect, correct and forget memory.

Permanent rule:

> Memory is evidence-backed owner data, not model intuition.

The model may propose memory. Jarvis decides whether it is eligible to persist. J0.3 authorizes the operation. J0.4 controls storage, classification, encryption, retention, deletion and external processing.

## 2. Non-goals

J0.5 does not implement J1 conversation UX, autonomous agents, provider-specific model routing, full tool execution, broad external integrations, or a production-scale recommendation engine. It does not create a second storage system. It must reuse and extend the J0.4 canonical memory, embedding, knowledge, provenance, lineage, retention and deletion structures.

## 3. Protected baseline

The exact protected source is main at `ae4ecb03cb9e658a00827dfb3ee8da1d0a88845d` with successful post-merge CI run `33737157654`.

The existing `@jarvis/memory` package already defines V2 classified memory records with provenance, confidence, consent, classification, retention, relationship and embedding references. The existing `@jarvis/knowledge` package is intentionally thin and is extended rather than replaced.

No J0.1–J0.4 authorization, ownership, encryption, secret-isolation, retention, deletion, backup, restore or privacy guarantee may be weakened.

## 4. Core memory model

### 4.1 Memory kinds

Canonical memory kinds remain compatible with the existing contract and are semantically defined as:

- `working`: short-lived task/session state; normally expires.
- `episodic`: a specific event or experience tied to time/source.
- `semantic`: a fact or proposition believed to be generally true.
- `project`: durable project-scoped state, decisions, constraints or milestones.
- `preference`: owner preference, style, choice or default.
- `procedural`: how-to/process/routine knowledge.
- `relationship`: facts about relationships between people/entities.
- `device`: facts about devices, capabilities or trusted-device context.

Legacy `conversation` memory remains a source record, not a preferred extracted memory kind.

### 4.2 Memory lifecycle states

Add explicit lifecycle semantics:

`PROPOSED → ACTIVE → SUPERSEDED | DISPUTED | EXPIRED | DELETION_REQUESTED → DELETED/PURGED`

Rules:

- Only ACTIVE records are eligible for normal retrieval.
- SUPERSEDED stays auditable and source-linked but loses retrieval priority.
- DISPUTED may be retrieved only when the conflict itself is relevant.
- EXPIRED is excluded from normal retrieval and follows J0.4 retention cleanup.
- DELETED/PURGED follow J0.4 deletion guarantees and derived-data invalidation.
- No hidden resurrection from embeddings, graph nodes, caches, export or obsolete backup.

### 4.3 Assertion status

Every durable memory must distinguish:

- `OWNER_ASSERTED`
- `OBSERVED`
- `IMPORTED`
- `MODEL_INFERRED`
- `DERIVED`

Model inference is never silently upgraded to owner assertion.

### 4.4 Confidence

Confidence is bounded `[0,1]` and is not enough alone to make a record authoritative. Retrieval ranking must consider source authority, verification, recency, scope, conflict state and task relevance.

### 4.5 Temporal validity

Memory supports:

- captured time,
- valid-from,
- valid-until,
- observed-at,
- verified-at,
- superseded-at.

A newer fact does not physically erase an older historical fact unless retention/deletion requires it.

## 5. Provenance and evidence

Every memory and knowledge relationship must be traceable to one or more evidence sources.

Supported provenance classes reuse and expand the current source taxonomy:

- owner input,
- conversation,
- file/imported document,
- website,
- tool observation,
- person,
- sensor/device,
- model inference,
- system derivation.

Requirements:

- canonical source ID and version,
- capture timestamp,
- confidence,
- optional verification timestamp,
- derived-from chain,
- no self-derivation,
- no circular lineage accepted by persistence layer,
- deleted source propagates invalidation/deletion obligations to derived artifacts according to J0.4 policy.

## 6. Memory admission engine

A proposed memory is evaluated deterministically before persistence.

Inputs:

- candidate kind and subject,
- source/provenance,
- owner/project scope,
- data classification,
- retention/external-processing policy,
- extraction confidence,
- duplicate/conflict candidates,
- consent and J0.3 authorization.

Decision outcomes:

- `ACCEPT`
- `ACCEPT_EPHEMERAL`
- `MERGE_WITH_EXISTING`
- `SUPERSEDE_EXISTING`
- `MARK_CONFLICT`
- `REQUIRE_OWNER_CONFIRMATION`
- `REJECT`

Hard rejection examples:

- D5 secret routed to generic memory,
- NEVER_STORE policy,
- cross-owner scope,
- missing provenance,
- unsupported classification/policy,
- malformed temporal interval,
- cyclic lineage,
- candidate that would weaken higher-level security/privacy policy.

## 7. Deduplication and canonicalization

J0.5 must avoid storing near-identical memories as unrelated facts.

Canonicalization rules include:

- normalized subject/entity identity,
- normalized predicate/semantic key where applicable,
- project/owner scope,
- temporal compatibility,
- source/version compatibility,
- exact-hash dedup before semantic similarity,
- semantic similarity may propose merge but cannot silently overwrite conflicting owner assertions.

Duplicate processing must be deterministic and idempotent.

## 8. Conflict detection and resolution

A conflict exists when two active propositions with compatible scope and subject cannot both be true for the same validity window.

Resolution precedence is policy-driven, not model whim. Default evidence order:

1. current explicit Owner correction/assertion,
2. verified authoritative observation/import,
3. prior Owner assertion,
4. corroborated observations,
5. model inference/derived memory.

Recency matters only when the proposition is time-varying.

Conflict outcomes:

- supersede older fact,
- preserve both as temporal history,
- mark disputed,
- request owner confirmation,
- reject low-authority contradictory inference.

All conflict transitions are auditable and source-linked.

## 9. Embeddings and semantic retrieval

Reuse pgvector-backed J0.4 embeddings as derived owner data.

Embedding metadata must include parent memory ID, source/provider/model, dimensions, version, data class, project/owner scope, created time and deletion state.

Requirements:

- embedding is invalid if parent is not retrieval-eligible,
- parent deletion invalidates/removes derived vector,
- cross-owner retrieval impossible,
- project filters applied before/with vector retrieval,
- classification/policy filters applied before context assembly,
- provider/model replacement does not change canonical memory identity,
- re-embedding creates a new derived version without mutating source truth.

## 10. Retrieval engine

Retrieval is hybrid and policy-aware.

Candidate sources:

- exact/structured lookup,
- project scope,
- entity/relationship lookup,
- lexical match,
- semantic vector similarity,
- recency/temporal relevance,
- relationship expansion.

Ranking features may include:

- task/query relevance,
- source authority,
- confidence,
- verification,
- recency where semantically appropriate,
- project scope,
- memory kind,
- conflict state,
- owner pin/priority,
- retrieval frequency only as a weak signal.

The retrieval engine must return scored evidence with reasons. It must never return only opaque text blobs.

## 11. Knowledge graph

Reuse J0.4 `knowledge.entities`, `knowledge.relationships`, `knowledge.relationship_evidence` structures.

### 11.1 Entity contract

Entities have:

- canonical ID,
- owner ID,
- optional project scope,
- entity type,
- canonical name,
- aliases,
- data class/policy,
- lifecycle/deletion state,
- provenance/evidence links,
- timestamps/version.

Entity types are extensible; examples include person, organization, project, device, place, document, concept, product, event.

### 11.2 Relationship contract

Relationships have:

- canonical ID,
- source entity,
- predicate/relation,
- target entity or typed literal,
- owner/project scope,
- valid time,
- confidence/status,
- provenance/evidence,
- source memory IDs,
- lifecycle/version.

### 11.3 Evidence

A relationship with no surviving evidence cannot remain silently authoritative. Evidence deletion or invalidation updates relationship confidence/status or removes it as required.

### 11.4 Graph queries

Minimum supported queries:

- neighbors/related entities,
- relationships by predicate,
- evidence for relationship,
- entities backed by memory/source,
- bounded multi-hop traversal with explicit depth/edge limits,
- temporal filtering,
- owner/project scope filtering.

Unbounded graph traversal is prohibited.

## 12. Personal context assembler

The Context Assembler is the privacy boundary between owner memory and model input.

Pipeline:

`REQUEST → IDENTITY/J0.3 AUTH → QUERY INTENT → CANDIDATE RETRIEVAL → OWNER/PROJECT FILTER → LIFECYCLE FILTER → CLASSIFICATION/POLICY FILTER → CONFLICT/TEMPORAL FILTER → RELEVANCE RANK → MINIMIZATION → DETERMINISTIC REDACTION → CONTEXT PACKAGE`

Context package contains:

- selected memory IDs,
- concise content or approved excerpts,
- provenance summary,
- confidence/status,
- temporal validity,
- why selected,
- excluded-count summary by reason,
- external-processing decision,
- no raw D5 secret.

External model rules inherit J0.4 policies:

- `LOCAL_ONLY`
- `PRIVATE_INFRASTRUCTURE`
- `APPROVED_EXTERNAL_AI`
- `SPECIFIC_PROVIDER_ONLY`
- `NEVER_EXTERNAL`

D5 secret material is never included in ordinary model context. Credentials/private keys/tokens are deterministically excluded. The model is not trusted to redact its own input.

## 13. Context budgets and minimization

Context assembly must accept explicit budgets:

- max memories,
- max graph facts,
- max characters/tokens estimate,
- max relationship depth,
- max age when applicable.

Budget overflow uses deterministic ranking/truncation rules and records what was omitted. Context must favor minimum sufficient evidence rather than maximum data disclosure.

## 14. Owner memory controls

J0.5 must expose service/API-level owner controls even if the final J1 UI does not yet exist.

Required operations:

- list/search memories,
- inspect one memory and its provenance,
- inspect source/derived chain,
- inspect conflicts/supersession history,
- correct memory,
- confirm/reject inferred memory,
- pin/unpin priority,
- change eligible retention where J0.3/J0.4 permit,
- forget one memory,
- forget by project/source/topic/entity where safe and bounded,
- show what context would be sent to a chosen processing class/provider policy,
- answer “what do you remember about X?” with evidence.

Owner correction creates a new authoritative version/history event rather than silently mutating audit evidence.

## 15. Authorization and privacy

All reads/writes/updates/deletes/context assembly pass through J0.3 capability and policy enforcement.

Minimum sensitive operations requiring explicit policy evaluation:

- D3+ memory read,
- memory correction,
- bulk forget,
- graph traversal over D3+,
- context assembly for external AI,
- owner memory export view,
- inferred-memory confirmation,
- cross-project retrieval.

No package may invent a parallel permission path.

## 16. Audit requirements

Audit records capture safe metadata only:

- memory proposed/admitted/rejected,
- conflict detected/resolved,
- memory corrected/superseded,
- retrieval request and selected IDs/counts,
- context assembly policy decision,
- forbidden item exclusion reason,
- graph mutation/traversal metadata,
- forgetting/deletion requests,
- owner confirmation/rejection.

Do not log raw D5 content, raw credentials or unnecessarily duplicate sensitive memory text.

## 17. Storage and migration rules

Use additive migrations where possible. Reuse existing J0.4 tables. New columns/tables are allowed only for missing J0.5 semantics such as lifecycle/version history, conflict sets, retrieval metadata or owner pins.

Migration rules:

- no destructive migration without J0.4 recovery-backed controls,
- migration must preserve all existing J0.4 records,
- indexes must support owner/project/status/temporal lookups,
- vector and graph indexes must remain provider-independent,
- rollback or forward-fix strategy documented,
- schema source of truth remains repository migrations.

## 18. Package architecture

Expected ownership:

- `@jarvis/memory`: contracts, admission, lifecycle, conflict handling, retrieval orchestration.
- `@jarvis/knowledge`: entity/relationship/evidence contracts and bounded graph services.
- `@jarvis/storage`: canonical persistence, pgvector, migrations, deletion/retention integration.
- `@jarvis/security`: existing J0.3 authorization only; no duplicate policy engine.
- `@jarvis/audit`: safe audit events.
- `@jarvis/core`: orchestration boundary and context assembly entry points where appropriate.
- `@jarvis/models`: only abstraction contracts needed for embeddings/context targets; J0.6 provider routing remains future work.

Dependency boundaries must remain acyclic and pass existing boundary checks.

## 20. Determinism requirements

Given identical persisted state, policy state, request and time reference, admission/conflict/context decisions must be reproducible.

LLMs may propose candidates or summaries, but the following remain deterministic system functions:

- permission checks,
- classification policy,
- NEVER_STORE/NEVER_EXTERNAL enforcement,
- secret exclusion,
- owner/project isolation,
- lifecycle eligibility,
- conflict precedence framework,
- deletion propagation,
- final context budget enforcement.

## 21. Failure behavior

Fail closed when:

- authorization unavailable,
- storage integrity uncertain,
- ciphertext/key invalid,
- policy cannot be resolved,
- owner/project scope ambiguous,
- provenance malformed,
- graph traversal exceeds bounded limits,
- vector index unavailable for an operation requiring semantic retrieval.

A vector outage may degrade to safe structured/lexical retrieval only when the request permits degraded operation and this is explicitly surfaced in result metadata.

## 23. J0.5 acceptance flow A–T

A. Baseline protection
- exact source commit verified,
- J0.1–J0.4 regressions green,
- branch only; main unchanged.

B. Owner-stated memory admission
- owner statement becomes ACTIVE memory with exact owner/project/provenance/classification/retention.

C. Non-memory conversation
- conversation that does not qualify remains stored only according to J0.4 policy and is not falsely promoted to durable memory.

D. Model inference isolation
- inferred candidate marked MODEL_INFERRED and cannot impersonate owner assertion.

E. NEVER_STORE and D5 rejection
- prohibited candidate creates no durable memory/vector/graph payload.

F. Duplicate/idempotent admission
- replay does not create duplicate canonical memory.

G. Semantic retrieval
- relevant memory retrieved through pgvector with owner/project filters and scored evidence.

H. Structured + semantic hybrid
- exact structured evidence outranks weak semantic similarity where appropriate.

I. Temporal supersession
- changed fact preserves history and retrieves the currently valid version.

J. Conflict detection
- contradictory facts create an explicit conflict/dispute or deterministic supersession according to evidence rules.

K. Owner correction
- owner correction becomes authoritative revision; prior history remains auditable but is not returned as current truth.

L. Knowledge entity extraction/linkage
- memory-backed entity created/reused with canonical identity and evidence.

M. Knowledge relationship evidence
- relationship links to supporting memory/source evidence and exposes provenance.

N. Bounded graph retrieval
- related facts retrieved within owner/project/depth/edge limits; scope leakage denied.

O. Context minimization
- context request returns only the highest-value minimum evidence under an explicit budget and records exclusions.

P. External privacy boundary
- mixed D1/D2/D3/D5/NEVER_EXTERNAL set sent toward synthetic external model; forbidden content excluded before provider boundary.

Q. Forget propagation
- owner forget removes/inactivates memory, vectors and unsupported derived graph state according to J0.4 deletion semantics.

R. Retention/expiry
- expired memory no longer participates in retrieval/context and cleanup propagates to derived vectors/graph evidence.

S. Failure/degraded retrieval
- vector/storage/policy failure fails closed or safely degrades only where explicitly permitted, with auditable metadata.

T. Audit and owner inspection
- owner can inspect what is remembered, provenance, conflicts and context preview; safe audit covers admission/retrieval/conflict/context/forget without raw prohibited payloads.

## 28. Exit rule

J0.5 succeeds only when Jarvis can prove, with persisted evidence and policy enforcement, what it remembers, why it remembers it, whether it is still valid, how it conflicts with other evidence, what it retrieves for a request, what it refuses to expose, and how the Owner can correct or forget it.

Only after J0.5 is merged and post-merge CI is successful may J0.6 become the next milestone. J1 remains locked until J0.12 Foundation v1 GO.
