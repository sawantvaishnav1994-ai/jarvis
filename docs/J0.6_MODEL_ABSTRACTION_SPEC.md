# J0.6 — Model Abstraction

Status: IMPLEMENTATION IN PROGRESS

Baseline: `16910231c5ff79bb0b34a15b86250f48575bedec` (J0.5 Development GO on `main`)

## Purpose

JARVIS is the permanent system. AI models are replaceable reasoning engines. J0.6 establishes a provider-neutral model boundary so identity, permissions, memory, private data, audit, and ownership never belong to or depend on one AI provider.

Permanent path:

`JARVIS request → J0.3 authorization/privacy policy → J0.5 minimum context → J0.6 model router → provider adapter → normalized result → verification → audit`

The LLM is never the permission engine, memory authority, secret store, or permanent source of JARVIS identity.

## Non-negotiable invariants

1. `main` remains protected by exact-commit CI; J0.6 develops only on its validation branch until controlled merge approval.
2. Provider replacement must not change permanent JARVIS data contracts.
3. D5 / never-external / disallowed external context must never cross an external provider boundary.
4. Provider credentials are vault references/handles, never prompt content or generic memory.
5. Model output is untrusted data until parsed/verified by JARVIS.
6. Models cannot grant themselves capabilities, approvals, tool access, or memory authority.
7. Routing must be deterministic for the same policy, capability, health, and budget inputs.
8. A fallback may never weaken privacy, security, capability, or owner policy.
9. Cancellation and timeouts must propagate to adapters.
10. Audit records model/routing metadata but does not require raw private prompt or secret content.
11. Unsupported critical model operations fail closed.
12. J1 remains locked until J0.12 Foundation v1 GO.

## Scope

### Provider-neutral contracts

J0.6 defines stable schemas for:

- model/provider identity,
- capabilities,
- input/output modality,
- context-window and output limits,
- privacy locality,
- structured-output support,
- streaming support,
- tool-call support metadata only (actual tools remain J0.7),
- token and monetary budgets,
- timeout/cancellation,
- normalized usage,
- normalized failures,
- routing decisions and evidence.

### Provider registry

A provider registry stores runtime adapter metadata independently from permanent user data. Each provider/model advertises capabilities rather than JARVIS hard-coding brand-specific behavior.

Expected classes include:

- LOCAL
- PRIVATE_REMOTE
- APPROVED_EXTERNAL

Provider/model status includes healthy, degraded, unavailable, and disabled.

### Privacy-aware routing

The router receives already-authorized/minimized context metadata and may only select providers compatible with the processing target and privacy policy.

Examples:

- local-only context → local provider only,
- approved-external context → approved external or stricter/local provider,
- disabled external AI consent → no external provider,
- D5 → no generic external model route.

J0.6 must not duplicate J0.5's context assembly logic. It consumes the J0.5 decision/package and enforces the provider boundary again as defense in depth.

### Capability-aware selection

Selection considers required capabilities such as text, reasoning, vision, structured output, streaming, and future tool-call planning metadata. A provider that cannot satisfy all required capabilities is ineligible.

### Budget-aware selection

A route may constrain:

- maximum input tokens,
- maximum output tokens,
- maximum total tokens,
- maximum estimated cost,
- timeout,
- allowed provider IDs/model IDs,
- local-only / external-allowed policy.

A fallback must still fit the remaining budget.

### Health, retries, timeout, and fallback

J0.6 distinguishes retryable transport/provider failures from permanent contract/policy failures.

Retries are bounded. Fallback ordering is explicit and deterministic. Policy/security/privacy failures are never retried through a weaker provider.

### Structured output

Structured responses are validated against a caller-supplied contract identifier/schema boundary. Invalid structured output is not silently accepted as trusted JARVIS state.

### Streaming and cancellation

Streaming-capable adapters expose normalized chunks/events. Owner/system cancellation and timeout abort the provider call and prevent later output from being committed as a successful result.

### Verification

J0.6 supports optional independent verification policies for high-value reasoning results. Verification is not authorization; it is a quality/safety signal and must remain bounded by the same privacy policy.

### Credentials

Adapters receive credential references through approved secret-execution boundaries. Generic model request objects must not contain API keys, passwords, refresh tokens, or raw vault secrets.

### Audit

Routing and execution audit records should support:

- request/correlation ID,
- selected provider/model,
- routing reasons,
- required capabilities,
- processing target/privacy class metadata,
- timing,
- normalized token/cost usage,
- retry/fallback events,
- success/failure category,
- cancellation/timeout,
- verification outcome.

Raw prompt contents are not required in model audit events.

## Initial J0.6 architecture

```text
J0.5 Context Package
        │
        ▼
ModelRequestEnvelope
        │
        ▼
ModelRouter
 ├─ policy/privacy eligibility
 ├─ capability eligibility
 ├─ health eligibility
 ├─ budget eligibility
 └─ deterministic scoring/order
        │
        ▼
ProviderRegistry
        │
        ├─ Local Adapter
        ├─ Synthetic/Mock Adapter
        ├─ OpenAI Adapter (later real connector)
        ├─ Anthropic Adapter (later real connector)
        ├─ Google Adapter (later real connector)
        └─ future adapters
        │
        ▼
Normalized ModelResult
        │
        ├─ schema/contract verification
        ├─ optional independent verifier
        └─ usage/cost/audit metadata
```

Real provider credentials/connectors are not required to prove the abstraction contract. J0.6 Development GO can use synthetic adapters plus negative tests proving provider substitution and privacy boundaries. Production provider onboarding remains separately controlled.

## Acceptance gates A–T

### A — Baseline protection
Exact J0.5 baseline and J0.1–J0.5 regressions remain green.

### B — Provider-neutral contracts
Equivalent requests/results can pass through different adapters without changing permanent JARVIS contracts.

### C — Capability registry
Provider/model capabilities are explicitly registered, validated, and queryable.

### D — Privacy eligibility
Processing locality and privacy policy exclude incompatible providers before invocation.

### E — Context boundary
Only the already-minimized authorized context package is accepted at the provider boundary; forbidden privacy markers are rejected defense-in-depth.

### F — Secret isolation
Model requests and audit records contain credential references only, never plaintext provider secrets.

### G — Deterministic routing
Identical eligible inputs produce the same provider/model choice and routing reasons.

### H — Local-only routing
Local-only/D5-equivalent restricted requests cannot select an external provider.

### I — Approved external routing
External providers are selectable only when explicit policy/consent and processing target permit them.

### J — Safe fallback
Fallback never weakens capability, privacy, owner allow/deny policy, or remaining budget.

### K — Bounded retry/timeout
Retries are bounded and only retry retryable failures; timeout/cancel terminates execution.

### L — Health/circuit behavior
Unavailable/disabled providers are excluded; degraded-provider behavior is explicit and deterministic.

### M — Token/cost budgets
Estimated and actual usage cannot silently exceed caller/owner budgets.

### N — Structured output validation
Malformed or schema-invalid structured output is rejected as untrusted output.

### O — Streaming/cancellation
Normalized streaming preserves ordering and cancellation prevents successful completion after abort.

### P — Provider substitution
At least two adapters satisfy the same provider-neutral contract, and swapping them leaves JARVIS-owned data unchanged.

### Q — Independent verification
Verification can use a distinct eligible model without granting authority or bypassing privacy rules.

### R — Safe audit
Audit captures routing/execution evidence while omitting prompt/secret payloads by default.

### S — Failure-safe degradation
No eligible provider / provider outage / malformed output produces explicit safe failure or permitted degradation, never silent policy bypass.

### T — Owner inspection/control
Owner-facing inspection can explain available providers, selection reasons, budget/health constraints, and disabled-provider state without exposing secrets.

## Development GO requirements

J0.6 Development GO requires an exact-commit GitHub Actions run on the validation branch proving:

- all existing J0.1–J0.5 tests remain green,
- full real PostgreSQL/pgvector integration remains green,
- startup and queue/readiness remain green,
- browser acceptance and J0.2 owner/device-trust flow remain green,
- outage/recovery and shutdown remain green,
- J0.4 A–S remains green,
- J0.5 A–T remains green,
- J0.6 A–T passes machine-verifiable acceptance.

No validation branch result merges automatically. Controlled merge to `main` requires explicit owner approval followed by exact-main CI success.

## Out of scope for J0.6

- J1 conversational UX/core,
- autonomous agents,
- direct tool execution (J0.7),
- proactive event processing (J0.8),
- production-grade external provider accounts/credentials,
- local model runtime installation on owner hardware,
- provider-specific permanent memory.

## Completion statement

J0.6 is complete only when JARVIS can demonstrably replace one model/provider with another while preserving identity, permissions, memory, privacy, data ownership, auditability, and fail-closed behavior.
