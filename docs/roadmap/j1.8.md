# J1.8 — Permission / Approval-Aware Conversation

Status: DEVELOPMENT

## Objective

Bridge J1.7 tool-aware conversation into the frozen J0 governance authority without creating a second approval, policy, risk or permit system.

## Canonical flow

`tool proposal -> J1.7 gateway attempt -> J0 approval required -> J1.8 pending approval envelope -> trusted Root Owner A3 decision -> exact binding revalidation -> J0 authorization/permit path -> J1.7 resume -> execution result -> conversation/audit`

## Authority boundaries

- J0 remains sole authority for capability, policy, risk, approvals, authorization permits, security epoch, ownership epoch and execution permission.
- J1.8 coordinates conversation state only. It never mints approval proof or execution permits.
- Models, agents and restricted actors cannot approve their own requests.
- Approval decisions require trusted Root Owner identity, live session/device binding and A3 evidence through the J0 authority adapter.
- Approval resume is bound to owner, project, conversation, session, turn, request, correlation and security epoch.
- Denied, expired, revoked, consumed or mismatched approvals never execute.
- Policy/risk/security changes remain revalidated by J0 before authorization/execution.
- J1.3 remains authoritative for model orchestration and J1.4 remains authoritative for the turn state machine.
- J1.5 remains authoritative for durable conversation/history metadata and J1.6 remains authoritative for memory-aware conversation coordination.
- J1.7 remains the only conversational bridge to the J0 UniversalToolGateway; J1.8 does not execute tools directly.

## Required behavior

1. Surface a structured `PENDING_APPROVAL` state when J1.7 reports `J17_APPROVAL_REQUIRED`.
2. Preserve exact request/conversation authority binding in the pending approval record.
3. Expose owner-decision coordination only through the trusted J0 approval authority port.
4. Require A3 owner decision evidence; no model/agent self-approval path exists.
5. Resume only an `APPROVED`, unexpired, exact-bound approval.
6. Pass only the J0-issued approval reference back to J1.7.
7. Preserve J1.7 idempotency, cancellation, untrusted-result and gateway boundaries.
8. Treat denial, expiry and revocation as terminal non-execution outcomes.
9. Reject cross-owner, cross-project, cross-conversation, cross-session, cross-turn and stale-security-epoch resumptions.
10. Preserve full inherited J0 + J1.0–J1.7 qualification.

## Qualification direction

J1.8 uses explicit A–T gates covering authority boundaries, owner A3 approval, exact-binding resume, denial/expiry/revocation, replay and race handling, epoch changes, emergency controls, J1.7 gateway-only execution, audit evidence and full real-stack regression.

The heavyweight qualification must remain reserved for a frozen exact J1.8 candidate. Development branches use the cheap J1 development gate first; tests are not weakened or skipped, only scheduled later for the exact candidate.

J1.9 operating modes must not start until J1.8 is merged, exact-main qualification is green, and J1.8 is declared COMPLETE + FROZEN. J1.10–J1.12 remain out of scope.

No production third-party credentials may be introduced during J1.8 development or qualification.
