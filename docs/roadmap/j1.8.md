# J1.8 — Permission / Approval-Aware Conversation

Status: COMPLETE + FROZEN

Closure note: J1.8 is part of the qualified J1 Core + Conversation v1 release lineage. The final J1 release baseline is `f75ed2d2d712fe32e64eb161a7ecab73dcb34db1`, which passed exact-candidate qualification in run `33974285835` and exact-main qualification in run `33974955058`.

## Objective

Bridge J1.7 tool-aware conversation into the frozen J0 governance authority without creating a second approval, policy, risk or permit system.

## Canonical flow

`tool proposal -> J1.7 gateway attempt -> J0 approval required -> J1.8 pending approval envelope -> trusted Root Owner A3 decision -> exact binding revalidation -> J0 authorization/permit path -> J1.7 resume -> execution result -> conversation/audit`

## Authority boundaries

- J0 remains sole authority for capability, policy, risk, approvals, authorization permits, security epoch, ownership epoch and execution permission.
- J1.8 coordinates conversation state only. It never mints approval proof or execution permits.
- Models, agents and restricted actors cannot approve their own requests, and owner-originated requests cannot self-approve through J1.8.
- Approval bindings preserve the requesting actor as well as owner, project, conversation, session, turn, request, correlation and security epoch.
- Approval decisions require trusted Root Owner identity, live session/device binding and A3 evidence through the J0 authority adapter.
- Before an owner decision is forwarded, J1.8 verifies the pending approval still belongs to that owner, is still pending, is unexpired, and was not requested by the same owner.
- A J0 decision response may change status only; mutating the bound requester/request/conversation/session/turn/project/epoch identity is rejected.
- Denied, expired, revoked, consumed or mismatched approvals never execute.
- Policy/risk/security changes remain revalidated by J0 before authorization/execution.
- J1.3 remains authoritative for model orchestration and J1.4 remains authoritative for the turn state machine.
- J1.5 remains authoritative for durable conversation/history metadata and J1.6 remains authoritative for memory-aware conversation coordination.
- J1.7 remains the only conversational bridge to the J0 UniversalToolGateway; J1.8 does not execute tools directly.

## Evidence-required inherited compatibility fixes

J1.8 real-gateway integration exposed two narrow inherited compatibility defects that must be corrected without changing authority or policy semantics:

1. J1.7 previously recognized only underscore-form gateway failure names such as `APPROVAL_REQUIRED`, while the J0.7 authorization bridge uses the governed reason `approval-required`. J1.7 now normalizes separator spelling before mapping gateway failures; the mapped state remains `J17_APPROVAL_REQUIRED` and all other authorization denials remain fail-closed.
2. J0.7 `UniversalToolGateway` previously collapsed the already-evaluated `approval-required` authorization state into generic `AUTHORIZATION_INVALID`, preventing a conversation layer from distinguishing a required owner ceremony from a denial. The gateway now preserves only that specific governed state as `APPROVAL_REQUIRED`; every other failed authorization still collapses to `AUTHORIZATION_INVALID`.

These fixes do not grant approval, bypass policy, weaken capability checks, consume proof, mint authorization, or execute a tool. They only preserve the J0-owned approval-required state across the existing J0.7 → J1.7 boundary. Because frozen inherited runtime files are touched, final J1.8 qualification must re-run the complete inherited J0/J1 stack before merge and again on exact `main`.

## Required behavior

1. Surface a structured `PENDING_APPROVAL` state when J1.7 reports `J17_APPROVAL_REQUIRED`.
2. Preserve exact requester/request/conversation authority binding in the pending approval record.
3. Expose owner-decision coordination only through the trusted J0 approval authority port.
4. Require A3 owner decision evidence; no model/agent/owner self-approval path exists.
5. Re-read approval state before deciding and reject owner mismatch, stale state, expiry and binding mutation.
6. Resume only an `APPROVED`, unexpired, exact-bound approval.
7. Pass only the J0-issued approval reference back to J1.7.
8. Preserve J1.7 idempotency, cancellation, untrusted-result and gateway boundaries.
9. Treat denial, expiry and revocation as terminal non-execution outcomes.
10. Reject cross-requester, cross-owner, cross-project, cross-conversation, cross-session, cross-turn and stale-security-epoch resumptions.
11. Preserve full inherited J0 + J1.0–J1.7 qualification.

## Qualification direction

J1.8 uses explicit A–T gates covering authority boundaries, requester binding, owner A3 approval, self-approval denial, exact-binding resume, denial/expiry/revocation, replay and race handling, epoch changes, emergency controls, J1.7 gateway-only execution, audit evidence and full real-stack regression.

The heavyweight qualification must remain reserved for a frozen exact J1.8 candidate. Development branches use the cheap J1 development gate first; tests are not weakened or skipped, only scheduled later for the exact candidate.

J1.9 operating modes must not start until J1.8 is merged, exact-main qualification is green, and J1.8 is declared COMPLETE + FROZEN. J1.10–J1.12 remain out of scope.

No production third-party credentials may be introduced during J1.8 development or qualification.
