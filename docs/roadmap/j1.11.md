# J1.11 — Conversational Web UI

Status: ARCHITECTURE FROZEN FOR DEVELOPMENT

Baseline: combined J1.10 internal checkpoint `fb3a55cb973c2a60af7788b46c782cba549ac734` on top of frozen J1.8 main.

## Objective

Provide an authenticated browser conversation surface for JARVIS without moving identity, session, operating-mode, model, tool, approval, persistence or emergency authority into JavaScript or the Web application.

The browser is a presentation/client adapter only. J0 remains identity/security/tool authority and J1.1–J1.10 remain the conversation runtime authorities.

## Browser security contract

- The browser never receives or supplies the Foundation session token. It remains HttpOnly.
- JavaScript cannot supply ownerId, deviceId, sessionId, securityEpoch, assurance or effective operating mode.
- Each turn is bound to the enrolled browser device through the existing J0.2 action-challenge/device-proof mechanism.
- The server computes the canonical turn-request SHA-256 digest. The existing read-only `identity.inspect` challenge carries that digest as optional input, so J0.2 binds the device/session proof to the exact turn request without adding a new Identity action or capability.
- Replayed, mismatched, expired, revoked or cross-context challenges fail through existing Identity validation.
- The Web proxy accepts only normalized turn fields and reconstructs the trusted backend request; untrusted authority-shaped fields are discarded by construction.
- Same-origin, JSON-only, bounded-body and no-store protections match the existing Identity proxy.
- The session cookie scope is widened only from `/api/identity` to `/api` so the sibling `/api/conversation` trusted server route can receive it; it remains HttpOnly, Secure and SameSite=Strict.

## UI contract

The conversation surface renders:

- user/assistant conversation content;
- ordered J1 response events;
- effective mode indicator;
- classification/privacy and local/external processing indicator;
- source/provider provenance;
- approval state;
- tool/result state and untrusted-result provenance when present;
- current security epoch metadata supplied by the trusted server;
- explicit SAFE/FREEZE/SHUTDOWN/revocation/session-expiry UX;
- reconnect/resume compatibility with J1.10 cursor semantics.

The UI never treats displayed approval/tool/model metadata as authority.

## J1.11 development adapter

J1.11 may use the local `SyntheticModelAdapter` only to prove the authenticated browser -> J1.2 context -> J1.3 orchestration -> J1.4 response/event -> browser rendering path. It must remain content-only: no tool, approval or memory side effect is committed by the J1.11 adapter.

This temporary content-only development adapter is not the J1 Core release path. J1.12 must replace/compose it with the complete J1.1–J1.10 persistence, memory, J1.7 tool, J1.8 approval, J1.9 mode, J1.10 resilience, audit/event and outage/recovery chain before final qualification.

## Required tests

- unauthenticated turn denied;
- browser cannot inject owner/session/device/epoch/mode authority;
- turn-request mutation between challenge and execution fails exact binding;
- stale/replayed device challenge fails;
- local content-only model response renders with provenance/privacy indicators;
- ordered events render monotonically;
- tool/approval absence is explicit rather than inferred;
- session expiry/device revocation returns a re-authentication state;
- emergency denial codes render as restricted UI state;
- no session token is exposed to JS/localStorage;
- browser acceptance verifies the conversation page and existing Identity flow still work.

## Milestone boundary

J1.11 does not claim final end-to-end release readiness. J1.12 owns the real-stack integration and adversarial release qualification.
