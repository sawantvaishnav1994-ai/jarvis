# J1.5 — Conversation Persistence & History

Status: DEVELOPMENT CANDIDATE

Baseline: frozen J1.4 main SHA `c454bc7f9198f3b9b549d2239183cd0d83c67ddf`.

## Objective

Make conversation history durable without weakening the J0 data-sovereignty boundary or duplicating sensitive plaintext. J1.5 persists owner-scoped conversation indexes, deterministic message ordering and terminal J1.4 result metadata while J0.4 `PrivateRecords` remains the encrypted source of truth for actual conversation/message payloads.

## Storage boundary

J1.5 adds runtime migration 0016 only. It does not rewrite Foundation migrations or J1.1 migration 0015.

`conversations.history_conversations` indexes an existing encrypted conversation record and binds it to owner, optional project, security epoch, state and optimistic version.

`conversations.history_messages` indexes existing encrypted message records with conversation, optional turn, role, monotonic ordinal and SHA-256 content digest. It never stores message plaintext.

`conversations.turn_results` stores terminal J1.4 state plus protected input/context/model/response digests and an optional encrypted response-message reference. It never stores response plaintext, prompt bodies or assembled context.

## Lifecycle and idempotency

Conversation registration is owner-scoped and exact-idempotent. Reusing the same conversation ID with changed project/security-epoch binding fails closed.

Archival uses optimistic versioning. Archived conversations reject new history-message appends.

Message append takes a row lock on the conversation, allocates the next ordinal transactionally and accepts only exact replay of an existing message ID. Changed replay fails closed.

Terminal turn-result persistence is exact-idempotent. A second write for the same owner/turn is accepted only when all protected fields match.

## History retrieval

Conversation listing uses stable `(updated_at, conversation_id)` cursor pagination and remains owner scoped.

Message history uses monotonic ordinal pagination and remains owner+conversation scoped.

The history service can be reconstructed after process restart entirely from PostgreSQL state; no in-process cache is authoritative.

## J1.4 binding

`ConversationHistoryService.persistPipelineResult` consumes J1.4 input/result metadata, verifies exact owner/conversation/turn binding, and hashes any response body before persistence. J1.4 remains the turn coordinator and J1.1 remains the authoritative session/turn state store.

## Security and sovereignty

- J0.4 `PrivateRecords` remains the encrypted payload source of truth.
- No generic J1.5 table stores prompt, context, message or model-response plaintext.
- Record-domain triggers require conversation/message references to match `storage.record_catalog`.
- Owner IDs are included in every history primary/foreign-key boundary.
- History IDs and digests never grant authority.
- Existing J0 retention, classification, consent, deletion and recovery controls continue to govern encrypted payload records.

## Validation

J1.5 requires dedicated unit, security and real PostgreSQL integration tests, including restart/reconstruction recovery, ordering, pagination, archive/version conflicts, exact replay behavior, cross-owner isolation and plaintext-exclusion checks.

The full inherited J0 and J1.0–J1.4 qualification remains mandatory. J1.5 DEVELOPMENT GO may only be recommended when A–T pass in the complete real-stack CI sequence.

## Non-goals

J1.6 memory-aware conversation is not part of J1.5. J1.7 tool-aware conversation and J1.8 approval-aware execution are not part of J1.5. J1.9 operating modes, J1.10 full streaming/resilience, J1.11 conversational UI and J1.12 final integration are not started here. No production model credentials or autonomous-agent authority are introduced.
