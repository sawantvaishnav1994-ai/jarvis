## Complete GO flow

A: existing owner authenticates; restricted Developer gets exact development grants.
B–C: read, development write and tests pass through issuance, consumption and verification.
D–E: production escalation waits for owner approval; denial never issues authorization.
F: missing authorization/direct tool call fails.
G–H: fresh passkey-approved exact deployment executes once; authorization/approval replay fails.
I–J: unrelated resource and self-approval fail.
K: lockdown overrides valid work; unauthorized release fails; owner release succeeds.
L: lower-level allow cannot override owner denial.
M: invalid policy cannot displace the existing secure active version.
N: exact versions, risk, approvals, use and emergency events are reviewed; database append-only protections are tested.

The same A–N flow runs against real PostgreSQL and through the browser/API.
The browser scenario retains the original J0.2 enrollment, delegation, revocation
and recovery assertions, adding J0.3 without replacing them.

## Scope interpretation

Production deployment is synthetic. A development capability never authorizes
production. An explicit owner policy may permit a proposal for the same registered
repository; fresh exact owner approval creates one request-bound authorization,
not a new standing capability. Budgets' resource/runtime/call limits still apply.

Hardware A4/P5 execution, real financial/external tools, hostile-code sandboxing,
host-level guaranteed termination and independent immutable archives remain later
production gates. The owner explicitly allowed mock J0.3 execution and deferred
full host containment. No Foundation v1 GO or J0.4 acceptance is implied.
