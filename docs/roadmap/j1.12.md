## Objective

J1.12 is the release-integration milestone for J1. It does not create a second identity, policy, risk, approval, permit, storage, memory, model, tool, event or audit authority. It composes the frozen J0 Foundation and J1.1–J1.11 contracts into one exact-SHA qualification and proves that failure, replay, revocation and recovery cannot create an alternate path.

## Canonical qualified chain

Root Owner → trusted device → authenticated Foundation session → J1 conversation session → operating mode → turn → context assembly → governed memory retrieval → model routing → ordered response stream → optional tool proposal → J0 permission/risk boundary → pending approval when required → trusted Root Owner A3 decision → J0 authorization/permit → J0.7 UniversalToolGateway execution → verified tool result → resumed response → conversation/history persistence → audit/events → authenticated Web UI.

J1.11's synthetic content-only adapter is development scaffolding only. J1.12 qualification must compose or replace that adapter with the inherited J1.5 persistence, J1.6 memory, J1.7 tool and J1.8 approval boundaries before release GO. A model result never becomes authority and the Web UI never receives or constructs Foundation session tokens, approval proofs, authorization permits or security epochs.

## Security and resilience invariants

- J0 remains sole authority for identity, device trust, sessions, policy, risk, approvals, authorization permits, security epoch, ownership epoch and UniversalToolGateway execution.
- Conversation/session identifiers supplied by a browser are continuity hints only. They are re-bound server-side to the authenticated owner, device, Foundation session and security epoch.
- Operating modes can reduce eligibility but cannot increase authority.
- Context and memory remain owner/project scoped, classification-aware, provenance-aware and retention-aware. D5 never enters generic/model context.
- NEVER_STORE content is not made durable by conversation history, retry, reconnect or failure recovery.
- Tool proposals are untrusted. Protected execution occurs only through J1.7 → J0.7.
- Approval is exact-bound and cannot be self-approved, replayed, raced, mutated or reused after consumption.
- Streaming/reconnect resumes ordered response events only; it never replays protected side effects.
- Duplicate requests and retries are idempotent or fail closed.
- Device removal, session revocation, security-epoch change, SAFE MODE, FREEZE and SHUTDOWN invalidate stale continuations.
- PostgreSQL, Redis, model/provider, tool and browser disconnect failures cannot create a bypass path.
- Recovery/restart cannot resurrect consumed approvals, stale permits, deleted memory or already-committed protected side effects.
- Audit/events correlate the chain without protected plaintext leakage.
