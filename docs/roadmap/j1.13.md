# J1.13 — Secure iPhone / PWA Access

Status: DEVELOPMENT / QUALIFICATION IN PROGRESS

Protected baseline: J1 Core + Conversation v1 frozen on `f75ed2d2d712fe32e64eb161a7ecab73dcb34db1`.

Candidate branch: `validation/j1.13-iphone-pwa-access-20260905`.

## Objective

Make the frozen J1 Core + Conversation Web surface usable from an iPhone over HTTPS without weakening the J0/J1 authority model.

## Security rule

The hosted iPhone client MUST NOT contain local vault material, model/provider credentials, database credentials, Redis credentials, trusted-device secrets, Foundation session tokens, permits, or server-derived authority fields. A public/static preview may render the UI but MUST NOT pretend to execute the private JARVIS runtime.

J0 remains sole authority for identity, policy, risk, approval, permits, security epoch, emergency controls and protected tool execution. J1.13 may expose a remote transport boundary; it may not create a second authority plane.

## Implemented remote boundary

The candidate now includes:

- standalone PWA metadata, manifest, generated icons and iPhone safe-area/responsive layout;
- an HTTPS Railway runtime that supervises the existing API, worker and Web processes;
- remote PostgreSQL with pgvector and Redis while preserving the frozen loopback runtime configuration shape;
- encrypted temporary runtime vault materialization with no browser-side secret exposure;
- secure remote passkey identity through `JARVIS_REMOTE_ORIGIN` and `JARVIS_REMOTE_RP_ID`;
- exact HTTPS origin and RP-ID validation with remote mode restricted to development;
- HttpOnly, Secure, SameSite-strict Foundation session cookies;
- non-exportable browser P-256 device keys and exact device-proof binding;
- server-derived conversation authority and exact turn-binding challenges;
- a governed return path from Identity to Conversation;
- fail-closed remote diagnostics that expose only safe error classification;
- stable identity-session persistence so conversation foreign-key binding references the actual Identity session ID rather than a token-hash storage key;
- compatibility migration for legacy token-hash-keyed Identity session rows;
- remote-specific regression coverage for identity-session storage and remote identity configuration.

## Verified live evidence

A real iPhone using Chrome reached the HTTPS Railway runtime and successfully:

- created and authenticated the Root Owner through passkey + device proof;
- established a privileged trusted-device binding and Foundation session;
- exercised expiry and re-authentication fail-closed behavior;
- opened the governed conversation surface;
- completed authenticated conversation turns through the J1 pipeline after the stable identity-session foreign-key fix.

The verified conversation response is provider-neutral/synthetic development output. Live external provider inference remains disabled and is not claimed by J1.13.

## Qualification rule

J1.13 is not complete merely because the PWA renders or the Railway runtime starts. The exact release candidate must pass the complete J1.13 qualification workflow, including inherited J0/J1 acceptance, PostgreSQL/pgvector, Redis, browser identity/device trust, expiry/revocation/emergency invalidation, conversation/session binding, privacy/NEVER_STORE, tool/approval/permit controls, audit correlation, restart/recovery and dependency outage/recovery.

After exact-candidate qualification, that exact SHA must be deployed and verified. `main` may then move only by non-force fast-forward to the exact qualified SHA. The exact `main` SHA must pass Foundation and full J1.13 qualification before J1.13 COMPLETE + FROZEN / GO may be issued.
