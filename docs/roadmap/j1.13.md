# J1.13 — Secure iPhone / PWA Access

Status: DEVELOPMENT / QUALIFICATION IN PROGRESS

Protected baseline: J1 Core + Conversation v1 frozen on `f75ed2d2d712fe32e64eb161a7ecab73dcb34db1`.

Candidate branch: `validation/j1.13-iphone-pwa-access-20260905`.

## Objective

Make the frozen J1 Core + Conversation Web surface usable from an iPhone over HTTPS without weakening the J0/J1 authority model.

## Security rule

The hosted iPhone client MUST NOT contain local vault material, model/provider credentials, database credentials, Redis credentials, trusted-device secrets, Foundation session tokens, permits, or server-derived authority fields. A public/static preview may render the UI but MUST NOT pretend to execute the private JARVIS runtime.

J0 remains sole authority for identity, policy, risk, approval, permits, security epoch, emergency controls and protected tool execution. J1.13 may expose a remote transport boundary; it may not create a second authority plane.

## Implemented remote boundary

The candidate now includes:

- standalone PWA metadata, manifest, generated icons and iPhone safe-area/responsive layout;
- an HTTPS Railway runtime that supervises the existing API, worker and Web processes;
- remote PostgreSQL with pgvector and Redis while preserving the frozen loopback runtime configuration shape;
- encrypted temporary runtime vault materialization with no browser-side secret exposure;
- secure remote passkey identity through `JARVIS_REMOTE_ORIGIN` and `JARVIS_REMOTE_RP_ID`;
- exact HTTPS origin and RP-ID validation with remote mode restricted to development;
- HttpOnly, Secure, SameSite-strict Foundation session cookies;
- non-exportable browser P-256 device keys and exact device-proof binding;
- server-derived conversation authority and exact turn-binding challenges;
- a governed return path from Identity to Conversation;
- fail-closed remote diagnostics that expose only safe error classification;
- stable identity-session persistence so conversation foreign-key binding references the actual Identity session ID rather than a token-hash storage key;
- compatibility migration for legacy token-hash-keyed Identity session rows;
- remote-specific regression coverage for identity-session storage and remote identity configuration.

## Verified live evidence

A real iPhone using Chrome reached the HTTPS Railway runtime and successfully:

1. authenticated the existing Root Owner with passkey plus enrolled device proof;
2. established a fresh HttpOnly Foundation session;
3. opened the governed conversation surface;
4. completed a `Hello JARVIS` turn through the authenticated J1 pipeline;
5. received HTTP 200 responses from the live `/api/conversation` boundary.

Before the successful turn, an expired/invalid session was rejected with HTTP 403 and `SESSION_INVALID`, confirming fail-closed behavior before re-authentication.

The successful current response source remains the development `synthetic-ui` / local provider path. J1.13 does not expand model authority or inject production/cloud credentials. Provider-neutral model success/failure/recovery remains an inherited qualification requirement.

## Fixed root cause

The first remote conversation attempts failed at conversation-session creation because `conversations.sessions.identity_session_id` references `identity.sessions(id)`, while the Identity repository had historically persisted session rows under the token hash rather than the stable `SessionRecord.id`.

The candidate now preserves token-hash lookup semantics in memory while persisting PostgreSQL rows under the stable session ID. Existing legacy rows are migrated transactionally. The foreign key and fail-closed conversation-session binding remain intact; no security check was removed or bypassed.

## Qualification gates

J1.13 uses `tests/acceptance/j1.13-gates.json` A–T. Qualification must prove, on the exact candidate and then exact main:

- exact frozen J1 baseline ancestry;
- no client-side secrets or server-derived authority;
- HTTPS origin/RP-ID passkey restrictions;
- Root Owner, trusted-device, Foundation-session and conversation-session exact binding;
- session expiry, revocation, device removal and security-epoch invalidation;
- challenge/proof replay and mutation rejection;
- CSRF/origin/direct-API fail-closed behavior;
- PostgreSQL/pgvector and Redis/BullMQ operation;
- inherited provider-neutral model success/failure/recovery;
- J1.7 → J0.7 protected tool execution and J1.8 approval/permit exact-binding semantics;
- NEVER_STORE, D5, privacy and protected-plaintext boundaries;
- correlated audit/events without protected plaintext leakage;
- restart and dependency outage/recovery behavior;
- full inherited J0 and J1 Core + Conversation regressions;
- no production credentials, no scope expansion, non-force merge and exact-main green before GO.
