# J1.6 — Memory-Aware Conversation

## Baseline

J1.6 starts only from the frozen J1.5 exact-main baseline:

`0fff75bd8ab4835c8a87b79ab8c9d639c3011eec`

J0 Foundation remains authoritative for identity, policy, security epoch, memory admission, memory lifecycle, memory retrieval, classified handling, audit and emergency controls. J1.1 remains authoritative for conversation/session/turn identity. J1.2 remains authoritative for context selection, disclosure eligibility, classification ceilings, retention boundaries, provenance, freshness, trust and context budget. J1.3 remains authoritative for model orchestration. J1.4 remains authoritative for turn lifecycle. J1.5 remains authoritative for durable conversation history.

## Objective

Make conversation turns memory-aware without creating a second memory authority and without allowing model output to write directly to long-term memory.

The required pre-model flow is:

`turn authority -> J1.5 history candidates -> approved J0 memory retrieval -> J1.2 ContextAssembler -> J1.3 model orchestration`

The required post-response flow is:

`response-derived candidate -> J1.6 authority binding -> J0 memory admission/evaluation -> J0 memory lifecycle authority`

## Runtime boundary

`MemoryAwareConversationService` is a coordinator only. It does not own a memory database, retrieval ranking authority, admission policy, long-term lifecycle, embedding store, or model provider.

The retrieval port represents the already-governed J0 memory retrieval authority. Returned packages must bind to the exact owner, project, turn and security epoch requested by the conversation authority. Any mismatch fails closed before context assembly.

Every retrieved memory item is converted to a J1.2 `ContextCandidateSource`. J1.2 therefore remains the final selection authority and can exclude D5, revoked/deleted, stale, expired, session-bound, disclosure-ineligible, untrusted, cross-owner, cross-project or budget-exceeding memory.

Degraded memory retrieval is explicit. The turn may continue with available safe context, but degradation status and reasons are propagated to the caller. Degraded retrieval never grants broader disclosure.

## Candidate admission

A response may produce a memory candidate, but J1.6 may only submit that candidate through the J0 admission port. Candidate owner, project, conversation, turn and security epoch must exactly match the active authority. Empty content and missing provenance fail closed.

Model output does not directly mutate a memory table. J0 admission can accept, keep ephemeral, merge, supersede, mark conflict, require owner confirmation or reject.

## Persistence

J1.6 introduces no database migration. Durable conversation history remains J1.5. Durable long-term memory remains the existing J0 memory subsystem.

## Security and sovereignty

J1.6 must preserve:

- exact owner/project/conversation/session/turn/security-epoch binding;
- J1.2 disclosure and classification enforcement;
- D5 denial from generic context;
- deletion/revocation enforcement;
- retention and session boundaries;
- provenance requirements;
- explicit degraded retrieval state;
- J0 memory admission authority;
- no direct provider calls outside J1.3;
- no tool execution before J1.7;
- no approval execution before J1.8;
- no J1.9 operating-mode implementation;
- no production model credentials.

## Validation

J1.6 requires dedicated unit and security tests plus the full inherited J0 and J1.0-J1.5 regression suite, real PostgreSQL/Redis stack, browser identity/device-trust acceptance, outage/recovery, shutdown verification and explicit A-T acceptance attestation.

Any candidate change after qualification requires a new SHA and a complete fresh qualification.

## Non-goals

J1.7 tool-aware conversation is not part of J1.6.

J1.8 approval-aware execution is not part of J1.6.

J1.9 operating modes, J1.10 streaming/resilience, J1.11 conversational UI and J1.12 final integration are not started by this milestone.

No production model credentials are introduced.
