# J1.1 Conversation + Session Engine

Status: DRAFT — J1.1 ONLY

Protected baseline: `3af4ee86c66f556f9eb68348f6923c796b386c15`

## Objective

Implement the smallest secure runtime that turns the J1.0 conversation contracts into a real owner-scoped conversation/session lifecycle while preserving all J0 Foundation authority boundaries.

J1.1 does not implement context assembly, model orchestration, memory-aware conversation, tool execution, or the final conversational UI.

## Required runtime boundary

1. Create/open/list owner-scoped conversations.
2. Bind conversation activity to the authenticated J0 session, trusted device, and current security epoch.
3. Create messages and turns with stable identifiers that never act as authorization.
4. Enforce a fail-closed turn state machine.
5. Enforce idempotency and reject duplicate/conflicting turn creation.
6. Support cancellation and revocation propagation.
7. Emit auditable lifecycle events without persisting prohibited plaintext.
8. Preserve D0-D5 and NEVER_STORE handling.
9. Fail closed on invalid owner, device, session, epoch, or mode state.
10. Recover consistently across API/worker restart and dependency outage.

## Schema decision

J1.1 is expected to need durable conversation/session/message/turn state. A migration may be introduced only after verifying the existing schema cannot safely represent these records. If required, it must be migration `0015`, preserve every existing Foundation invariant, and add only J1.1 runtime storage.

## Mobile compatibility requirement

All J1.1 APIs and session semantics must be client-neutral so the same secure backend can later serve desktop web and the owner's phone. J1.1 does not expose JARVIS publicly or add a native mobile app.

## Explicit exclusions

- J1.2 context assembly
- production model calls or credentials
- memory retrieval/write orchestration beyond existing Foundation hooks
- direct model-to-tool execution
- production external connectors
- native iOS/Android implementation
- broad autonomous behavior
- weakened permissions, approvals, classification, NEVER_STORE, emergency, or audit controls

## Acceptance direction

J1.1 must be qualified against an explicit A-T catalogue that covers ownership isolation, trusted-device/session/epoch binding, lifecycle correctness, state-machine transitions, duplicate/idempotent requests, cancellation/revocation, NEVER_STORE, audit/event correlation, restart/outage recovery, concurrency, emergency controls, Foundation regression, schema integrity, and milestone boundary enforcement.
