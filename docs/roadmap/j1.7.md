# J1.7 — Tool-Aware Conversation

## Baseline

J1.7 starts only from the frozen J1.6 exact-main baseline:

`e6657e7f8fea1c01549db65b924c79a6c5048a7c`

J0 Foundation remains authoritative for identity, capability, policy, risk, approval consumption, permits, classified handling, credentials, tool registry, tool execution, audit and emergency controls. J1.1 remains authoritative for conversation/session/turn identity. J1.2 remains authoritative for context selection and disclosure. J1.3 remains authoritative for model orchestration. J1.4 remains authoritative for the turn state machine. J1.5 remains authoritative for durable conversation history. J1.6 remains authoritative for memory-aware coordination through J0 memory.

## Objective

Allow a governed conversation turn to use model-generated tool planning without allowing a model or conversation layer to execute tools directly.

Required flow:

`J1.3 structured tool proposal -> J1.7 proposal validation -> trusted conversation authority binding -> J0.7 registry/capability/policy/risk/approval boundary -> J0.7 UniversalToolGateway -> validated untrusted tool result -> conversation continuation`

The model proposes intent only. It does not provide or control owner identity, project authority, conversation/session/turn identity, security epoch, external-disclosure authority, approval authority, credentials or policy decisions.

## Runtime boundary

`J17ToolAwareConversationService` is a coordinator only. It does not own a tool registry, capability system, policy engine, approval authority, permit authority, credential store, retry engine, idempotency store, audit store or adapter execution runtime.

J1.7 consumes J1.3 structured output through a narrow `ConversationToolProposal` contract. The proposal may contain only tool id/version, operation, input, resource, privacy class, requested mode and an execution idempotency key.

Trusted caller state injects owner/project/conversation/session/turn/security-epoch binding, actor identity, execution budget, deadline, external-disclosure permission and any approval reference.

## J0.7 gateway authority

All execution routes through the existing J0.7 gateway contracts. J1.7 must not call an adapter directly.

The J0.7 gateway remains responsible for:

- tool registration and health;
- operation and capability metadata;
- input schema validation;
- classification/privacy enforcement;
- policy/risk evaluation;
- approval/authorization binding;
- security/emergency revalidation;
- credential leasing;
- cost limits;
- idempotency and concurrency;
- retries and unknown-outcome handling;
- cancellation and timeout;
- output schema validation;
- verification/reconciliation/rollback where supported;
- audit events.

## Model proposal restrictions

J1.7 accepts only `INSPECT`, `SIMULATE`, `DRY_RUN` and `EXECUTE` from model planning. Model-originated `VERIFY_ONLY`, `RECONCILE` and `ROLLBACK` are not admitted by this conversation proposal contract in the initial J1.7 runtime.

`EXECUTE` requires an idempotency key before the gateway is invoked. The gateway still applies its own stricter side-effect/idempotency rules.

Model output cannot set authority or approval fields. Unknown fields fail strict proposal parsing.

## Approval boundary

J1.7 may surface `J17_APPROVAL_REQUIRED`, but it does not create, approve or consume a new approval authority of its own. Existing J0 approval enforcement remains authoritative. Full conversational permission/approval lifecycle belongs to J1.8.

Any approval reference used by J1.7 is supplied by trusted caller state, bound by J0.7 authorization, and cannot come from model output. `approvalCommitted` remains false in J1.7 coordinator results.

## Result handling

Tool results must bind to the exact request id, tool id, version and operation sent to the J0 gateway. Tool output remains explicitly `UNTRUSTED_EXTERNAL_DATA` and must be treated as data, not executable instructions.

A successful `EXECUTE` may set `toolExecutionCommitted: true` when J0.7 reports `SUCCEEDED` or `VERIFIED`. It may also be true for `RECONCILED` only when J0.7 independently reports the reconciled effect as verified. An unresolved `UNKNOWN_OUTCOME` never becomes a committed result. Simulation/dry-run/inspection never count as committed execution.

## J1.4 integration

The frozen J1.4 runtime remains unchanged. Its historical invariant `toolExecutionCommitted:false` continues to protect the original content-only turn path.

`J17CapturingModelPort` wraps the existing J1.4 model port without modifying J1.4. `J17ToolAwareTurnCoordinator` first runs the existing J1.4 turn state machine, consumes the exact captured J1.3 result only after a completed turn, ignores ordinary structured content, and invokes J1.7 only when the captured result declares `kind: "tool-proposal"`.

This bridge preserves J1.4 authority checks and state transitions. J1.4 itself still reports no tool or approval commitment; J1.7 records any governed tool execution separately after the frozen turn boundary.

## Persistence

J1.7 introduces no new database migration in the initial runtime. Existing J0 audit/execution evidence and J1.5 conversation history remain authoritative for their domains.

## Development validation strategy

Normal J1.7 development pushes use the low-cost `J1 Development Checks` workflow only: focused formatting, package type build, strict test typecheck and targeted J1.7/inherited security tests. Heavy PostgreSQL/Redis/browser/Root-Owner/recovery/A-T qualification is reserved for a frozen J1.7 candidate and exact-main post-merge qualification.

This changes when expensive validation runs, not what the final qualification must prove.

## Final qualification requirements

Before J1.7 can be declared complete, a frozen exact candidate must add explicit A-T acceptance gates and prove at minimum:

- exact J1.6 baseline ancestry;
- no second tool gateway or policy/approval authority;
- strict model proposal schema;
- exact authority/turn/security-epoch binding;
- no model-controlled approval or external-disclosure authority;
- capability/policy/risk path through J0.7;
- approval-required and approval-mismatch fail-closed behavior;
- idempotency and replay protection;
- cancellation, timeout, unknown-outcome and emergency-stop behavior;
- privacy/classification enforcement including D5 restrictions;
- malformed-output rejection and prompt-injection-shaped output remaining untrusted;
- no direct adapter/provider/credential bypass;
- J1.4 state-machine compatibility through the explicit bridge;
- dedicated unit, integration and adversarial security coverage;
- full inherited Foundation and J1.0-J1.6 regression qualification;
- real PostgreSQL/Redis stack, browser identity/device trust, outage/recovery and clean shutdown;
- exact-main post-merge qualification.

## Non-goals

J1.8 full permission/approval-aware conversational lifecycle is not part of J1.7.

J1.9 operating modes, J1.10 streaming/cancellation UI semantics, J1.11 conversational web UI and J1.12 final integration qualification are not started by this milestone.

No production third-party tool credentials are introduced by J1.7 development.
