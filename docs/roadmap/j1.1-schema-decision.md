# J1.1 Conversation & Session Engine — Schema Decision

Status: ACCEPTED FOR J1.1 DEVELOPMENT
Date: 2026-09-04
Baseline: J1.0 main `3af4ee86c66f556f9eb68348f6923c796b386c15`

## Decision

J1.1 requires an additive migration `0015_conversation_session_engine.sql`.

The existing J0.4 storage substrate already provides durable, encrypted owner-data records for `conversation` and `message` through `storage.record_catalog`, `conversations.conversations`, and `conversations.messages`. Those tables remain the canonical durable content substrate and MUST NOT be replaced or weakened.

However, J1.1 needs authoritative runtime coordination state that is not represented by the generic owner-data records: trusted-session bindings, security epoch snapshots, turn lifecycle/state, idempotency keys, cancellation state, and concurrency/version guards. Encoding those authority-bearing fields only inside encrypted generic payloads would make database-enforced uniqueness, atomic lifecycle transitions, replay protection, restart recovery, and revocation checks weaker and harder to prove.

Therefore migration 0015 will add only the minimum relational coordination tables required for J1.1 runtime authority. It will reference the existing conversation/message records rather than duplicate their content.

## Required relational state

1. `conversations.sessions`
   - session id
   - owner id
   - actor/principal id
   - trusted device id
   - authentication/session binding id
   - security epoch snapshot
   - operating mode snapshot/reference
   - status and revocation/cancellation timestamps
   - created/last-seen timestamps
   - optimistic version

2. `conversations.turns`
   - turn id
   - owner id
   - conversation id referencing the existing conversation record
   - session id
   - input message id referencing the existing message record when durable
   - lifecycle state
   - idempotency key
   - correlation id
   - cancellation/revocation reason code
   - created/updated/completed timestamps
   - optimistic version

No model response body, prompt body, message content, tool result, memory content, secret, credential, or NEVER_STORE payload may be placed in these coordination tables.

## Security requirements

- Owner isolation is mandatory on every lookup and mutation.
- Conversation/session/message/turn IDs are locators, never authorization.
- Session validity depends on the current J0 identity/device/security-epoch authority; a stored snapshot never overrides current authority.
- Device revocation, session revocation, epoch invalidation, FREEZE, SAFE MODE, and SHUTDOWN must prevent prohibited continuation.
- Idempotency uniqueness must prevent duplicate accepted turns for the same owner/session boundary.
- Turn state transitions must use atomic compare-and-set/optimistic version checks.
- Cancellation is monotonic: a cancelled/terminal turn cannot silently return to an executable state.
- `NEVER_STORE` and `DELETE_AFTER_SESSION` content remains transient. Coordination rows may contain only payload-free identifiers/status necessary for safe execution and must obey the J1.0 retention contract.
- D5 remains outside generic conversation persistence.
- PUBLIC privileges remain revoked.

## Migration policy

- Existing migrations 0001–0014 are immutable.
- 0015 is additive only.
- Fresh install from zero and accepted-baseline upgrade from schema 14 must both pass.
- Migration failure must fail closed and must not leave a falsely-current schema marker.
- Foundation schema manifest/history changes, if required by the governed migrator, must be additive J1 metadata and must not rewrite historical hashes.

## Non-goals

Migration 0015 does not implement context assembly, memory retrieval, model orchestration, tool execution, approval continuation, streaming transport, or the final chat/mobile UI. Those remain later J1 milestones.

## Why this is required

J1.1 is the authority-bearing conversation/session backbone. Durable conversation and message content already exists, so duplicating it would be wrong. Runtime authority does not yet exist, so pretending the generic payload tables are sufficient would weaken concurrency, replay, recovery, and revocation guarantees. A minimal additive coordination migration preserves J0 storage while giving J1.1 enforceable runtime semantics.
