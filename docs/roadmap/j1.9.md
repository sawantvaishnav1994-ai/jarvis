# J1.9 — Operating Modes

Status: ARCHITECTURE FROZEN FOR DEVELOPMENT

Baseline: `cf203bb71df1d4cb19e819546f2684201e04cc16` (J1.8 COMPLETE + FROZEN)

## Objective

Add explicit conversational operating modes that constrain how JARVIS may reason, propose actions, request approvals, and execute already-governed tool work without creating a second policy, risk, approval, permit, identity, memory, model, or tool authority.

J1.9 is a coordination layer. J0 remains the security and execution authority. J1.3 remains model orchestration authority, J1.4 remains turn-state authority, J1.5 history authority, J1.6 memory-aware coordination, J1.7 tool-aware execution bridge, and J1.8 approval-aware coordination.

## Initial mode set

1. `ADVISORY` — answer, analyze, plan, and explain; no tool execution is committed.
2. `ASSISTED` — tools may be proposed and executed only through the existing J1.7/J1.8/J0 governed path; approval requirements remain unchanged.
3. `AUTONOMOUS_BOUNDED` — eligible actions may proceed within an explicitly granted, bounded operating envelope, but every action still passes capability, policy, risk, approval/permit, epoch, emergency, and tool-gateway controls.
4. `SAFE` — fail-closed conversational mode: no external side-effecting execution; read-only behavior is allowed only where J0 policy explicitly permits it.
5. `FROZEN` — no new action execution or approval initiation; preserve inspection/audit/status behavior only.

`SHUTDOWN` remains a J0 emergency-control state, not a J1.9 conversational mode. J1.9 must honor it immediately and cannot downgrade or override it.

## Canonical flow

`authenticated turn -> resolve requested/effective mode -> bind mode to owner/project/conversation/session/turn/security epoch -> J1.2 context -> J1.3 model -> mode capability filter -> J1.7 tool-aware path -> J1.8 approval-aware path when required -> J0 authorization/permit/tool gateway -> result -> response -> persistence/audit`

## Authority rules

- The model may request or recommend a mode but cannot self-grant a more permissive mode.
- A mode never grants a capability that J0 denies.
- A mode never suppresses a J0 approval requirement.
- A mode never mints an approval reference, authorization, permit, credential, or security epoch.
- A more permissive effective mode requires trusted authority evidence appropriate to the requested scope.
- Security epoch, device trust, owner/project/session binding, emergency state, policy, risk, and revocation are revalidated by existing J0 boundaries.
- Mode state is scoped and explicit; no hidden global mutable mode may silently widen authority.
- Cross-owner, cross-project, cross-conversation, cross-session, cross-turn, stale-epoch, replayed, expired, or revoked mode authority fails closed.
- Mode transitions are auditable and deterministic.
- `SAFE`, `FROZEN`, or J0 emergency controls take precedence over a previously granted permissive mode.

## Required runtime contracts

J1.9 development should introduce typed contracts for:

- requested mode and effective mode;
- mode scope/binding;
- mode transition request and decision;
- bounded autonomous envelope where applicable;
- mode evaluation result and denial reason;
- mode-aware tool/action eligibility;
- audit/event evidence for transition and enforcement.

The contracts must carry owner, project when present, conversation, session, turn, actor/request correlation, security epoch, issuance/expiry where applicable, and provenance/authority evidence.

## Enforcement direction

### Advisory

- Model generation is allowed under existing J1.3 controls.
- Tool intent may be represented for explanation/planning, but execution must not be committed.
- No approval ceremony should be opened merely for a hypothetical/advisory action.

### Assisted

- Existing J1.7 tool-aware flow is available.
- Existing J1.8 approval ceremony is mandatory whenever J0 requires it.
- No new execution shortcut exists.

### Autonomous bounded

- Requires an explicit bounded envelope and trusted authority binding.
- Envelope constraints may narrow allowed tool/action classes, cost, external side effects, time, project, conversation, or other governed scope.
- The envelope cannot override J0 capability/policy/risk/approval/permit/emergency decisions.
- Out-of-envelope actions fail closed or fall back to the existing approval-aware path only when J0/J1.8 explicitly permits that transition.

### Safe

- External side effects are blocked at the J1.9 coordination layer before reaching execution.
- J0 remains authoritative and may impose stricter restrictions.
- Safe mode cannot be used to bypass audit, identity, or disclosure controls.

### Frozen

- No new tool execution and no new approval initiation.
- Existing audit/status inspection remains available only through allowed read paths.
- In-flight/late results must not be committed merely because they were initiated before the freeze; existing J0/J1.10-compatible cancellation/revalidation foundations remain authoritative.

## Transition rules

- Same or more restrictive transitions may be accepted only when their binding is valid and they do not conflict with J0 emergency state.
- More permissive transitions require explicit trusted authority; model/agent/service self-escalation is forbidden.
- Transition decisions are bound to exact scope and security epoch.
- Replayed or stale transition evidence is rejected.
- Emergency or epoch changes invalidate permissive assumptions immediately.
- No transition may silently mutate the approval/tool request binding established by J1.7/J1.8.

## Security/adversarial requirements

Tests must cover at minimum:

- model attempts to self-escalate mode;
- agent/service/delegate escalation without authority;
- cross-owner/project/conversation/session/turn mode replay;
- stale security epoch and removed device trust;
- expired/revoked bounded autonomous envelope;
- autonomous envelope scope/cost/action overflow;
- SAFE/FROZEN execution attempts;
- approval bypass attempts in ASSISTED/AUTONOMOUS_BOUNDED;
- J0 emergency state precedence;
- duplicate transition requests and transition races;
- late tool result after restrictive mode transition;
- restart/recovery preserving fail-closed semantics;
- malformed/untrusted mode metadata from model/tool/provider output.

## Milestone boundaries

J1.9 must not implement J1.10 streaming/cancellation/resilience, J1.11 conversational Web UI, or J1.12 final integration qualification. It may define compatibility contracts needed for those later stages, but must not start their runtime scope.

No production third-party credentials may be introduced.

## Development and qualification strategy

Use lightweight J1 development CI during implementation. Do not launch the full real-stack qualification after each code change.

Before J1.9 can be COMPLETE + FROZEN:

1. dedicated unit/integration/security tests must be green;
2. explicit J1.9 A–T gates must exist;
3. one exact frozen candidate must pass the full real stack with inherited J0 + J1.0–J1.8 regression;
4. `main` must still equal the frozen J1.8 baseline before merge;
5. merge must be a non-force fast-forward to the exact qualified candidate;
6. exact-main consolidated qualification must pass through J1.9 A–T;
7. only then may J1.10 begin.
