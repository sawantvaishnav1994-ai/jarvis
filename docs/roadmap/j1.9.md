# J1.9 — Operating Modes

Status: ARCHITECTURE FROZEN FOR DEVELOPMENT

Baseline: `cf203bb71df1d4cb19e819546f2684201e04cc16` (J1.8 COMPLETE + FROZEN)

## Objective

Project the frozen J0/Foundation operating-mode and emergency-control authority into conversation behavior without creating a second mode, policy, risk, approval, permit, identity, memory, model, or tool authority.

J1.9 is a coordination/enforcement layer. J0 remains authoritative for operating-mode definitions, emergency controls, security epoch, policy and execution. J1.3 remains model orchestration authority, J1.4 turn-state authority, J1.5 history authority, J1.6 memory-aware coordination, J1.7 tool-aware execution bridge, and J1.8 approval-aware coordination.

## Canonical Foundation mode set

J1.9 MUST use the frozen `foundation/operating-modes-v1.json` mode identifiers exactly:

1. `Assistant` — reactive assistant; tool work is suggest/prepare by default and all execution remains governed.
2. `Copilot` — owner-supervised governed execution within permission.
3. `Autonomous` — explicitly authorized, bounded and audited autonomy; sensitive/critical actions remain governed.
4. `Focus` — task/focus-scope-only behavior with minimum necessary disclosure.
5. `Private` — local-first/restricted network, tool and disclosure behavior.
6. `Guest` — restricted, non-privileged, no owner-sensitive authorization.
7. `Safe` — restricted, non-mutating or explicitly-safe behavior; autonomy disabled.
8. `Emergency` — emergency-policy-only behavior; autonomy disabled and capability may be stopped.

J1.9 MUST NOT introduce a parallel `ADVISORY`, `ASSISTED`, `AUTONOMOUS_BOUNDED`, `SAFE`, or `FROZEN` authority vocabulary. Where conversational behavior resembles those concepts, it is derived from the canonical Foundation mode and emergency-control state.

## Canonical emergency controls

The frozen J0 controls are:

- `PAUSE`
- `FREEZE`
- `DISCONNECT`
- `SAFE MODE`
- `REVOKE`
- `SHUTDOWN`

These controls only reduce or terminate capability and always override conversational intent. J1.9 cannot downgrade, clear, reinterpret, or bypass them.

## Canonical flow

`authenticated turn -> resolve Foundation mode snapshot -> resolve J0 emergency state -> bind owner/project/conversation/session/turn/security epoch -> J1.2 context -> J1.3 model -> J1.9 mode filter -> J1.7 tool-aware path -> J1.8 approval-aware path when required -> J0 authorization/permit/tool gateway -> result -> mode/emergency revalidation -> response -> persistence/audit`

## Authority rules

- Foundation mode identifiers and transition semantics are authoritative and immutable to J1.9.
- The model may describe or recommend a mode but cannot transition mode or increase authority.
- A mode never grants a capability J0 denies.
- A mode never suppresses a J0 approval requirement.
- A mode never mints approval references, authorization, permits, credentials, security epochs, or emergency-control state.
- Any transition that can increase effective authority requires trusted J0 authority evidence.
- Security epoch, owner/project/session/device binding, emergency state, policy, risk and revocation are revalidated at existing J0 boundaries.
- Mode state is explicitly scoped; no hidden process-global mutable state may widen authority.
- Cross-owner/project/conversation/session/turn, stale-epoch, replayed, expired or revoked mode evidence fails closed.
- `Safe`/`Emergency` modes and J0 `PAUSE/FREEZE/DISCONNECT/SAFE MODE/REVOKE/SHUTDOWN` controls take precedence over less restrictive assumptions.
- Pending J1.8 approvals and previously prepared J1.7 tool requests do not survive a restrictive mode/emergency change without full current-authority revalidation.

## Required runtime contracts

J1.9 introduces typed coordination contracts for:

- canonical Foundation mode snapshot;
- emergency-control snapshot;
- exact owner/project/conversation/session/turn/security-epoch binding;
- requested transition and J0-issued transition decision/evidence;
- bounded autonomy envelope for `Autonomous` where supplied by J0 authority;
- mode-aware model/tool/approval eligibility;
- denial/restriction reasons;
- audit/event evidence for mode enforcement.

J1.9 stores no second authoritative mode database.

## Enforcement matrix

### Assistant

Model generation is allowed under existing controls. Tool proposals may be represented, but execution remains J1.7/J1.8/J0 governed and must not become autonomous implicitly.

### Copilot

Governed execution may proceed through J1.7. J1.8 approval remains mandatory whenever J0 requires it. Owner supervision never substitutes for policy/permit checks.

### Autonomous

Requires explicit current J0-backed autonomy authority/envelope. The envelope can only narrow tool/action class, cost, disclosure, time, project, conversation or other governed scope. Every action still passes capability, policy, risk, approval/permit, epoch, emergency and UniversalToolGateway controls.

### Focus

Context, tools, network and background behavior are constrained to the trusted focus/task scope. Out-of-scope action fails closed rather than silently widening the focus scope.

### Private

Network/disclosure/tool behavior remains restricted according to Foundation/J0 privacy policy. J1.9 cannot reinterpret Private mode as consent for external disclosure.

### Guest

Owner-sensitive approval/authorization is unavailable to the guest actor. Privileged tool execution and cross-owner memory/context access remain denied.

### Safe

Autonomy is disabled. Mutating/external side effects are denied before dispatch unless J0 explicitly classifies the action as safe under current policy. J0 can impose stricter restrictions.

### Emergency

Only emergency-policy-authorized behavior may proceed. Emergency controls can pause, freeze, disconnect, revoke or shut down work immediately.

## Emergency precedence

- `SHUTDOWN` denies acceptance/continuation of governed work requiring active execution.
- `REVOKE` invalidates affected authority.
- `FREEZE` denies new governed action commitment and requires late/in-flight work to revalidate before any result can be committed.
- `SAFE MODE` forces safe-mode restrictions regardless of a previously less restrictive conversational mode.
- `DISCONNECT` prevents network-dependent execution where the J0 control applies.
- `PAUSE` prevents progression requiring active execution until current J0 authority permits continuation.

J1.10 owns richer streaming/cancellation/resilience mechanics; J1.9 only defines and enforces the fail-closed mode/emergency compatibility boundary.

## Transition rules

- J1.9 never commits a mode transition itself; it accepts only a transition result/evidence from an injected J0 authority port.
- Same/more-restrictive requests do not bypass J0 transition authority.
- More-permissive transitions require explicit trusted authority; model/agent/service self-escalation is forbidden.
- Transition decisions are bound to exact scope and security epoch.
- Replayed/stale transition evidence is rejected.
- Emergency or epoch changes invalidate permissive assumptions immediately.
- No transition may mutate J1.7/J1.8 request/approval bindings.

## Security/adversarial requirements

Tests must cover at minimum:

- model-supplied or provider/tool-supplied fake mode metadata;
- agent/service/delegate escalation without J0 transition authority;
- cross-owner/project/conversation/session/turn mode replay;
- stale security epoch and revoked authority;
- expired/revoked `Autonomous` envelope;
- autonomy scope/cost/action overflow;
- Focus scope overflow;
- Private disclosure/network bypass;
- Guest privileged-action/owner-approval attempts;
- Safe mutating execution attempts;
- Emergency and each J0 emergency-control precedence path;
- approval pending then restrictive mode/control change;
- duplicate transition requests and transition races;
- late tool result after restrictive transition;
- restart/recovery preserving fail-closed semantics;
- no direct model/provider/tool transition execution.

## Milestone boundaries

J1.9 must not implement J1.10 streaming/cancellation/resilience, J1.11 Web UI, or J1.12 final integration qualification. It may define compatibility contracts needed later, but must not start their runtime scope.

No production third-party credentials may be introduced.

## Development and qualification strategy

Use lightweight J1 development CI during implementation. Do not launch full real-stack qualification after each code change.

Before J1.9 can be COMPLETE + FROZEN:

1. dedicated unit/integration/security tests are green;
2. explicit J1.9 A–T gates exist;
3. one exact frozen candidate passes the full real stack with inherited J0 + J1.0–J1.8 regression;
4. `main` still equals frozen J1.8 before merge;
5. merge is a non-force fast-forward to the exact qualified candidate;
6. exact-main consolidated qualification passes through J1.9 A–T;
7. only then may J1.10 begin.
