## Objective

Define the complete architectural and security contract for JARVIS Core + Conversation before runtime implementation begins. J1.0 must reuse Foundation v1 as the sole authority for identity, device trust, sessions, policy, risk, approvals, permits, classified storage, memory, model-provider abstraction, tool gateway, events, audit, emergency controls, recovery and security epoch semantics.

J1.0 is a specification/freeze milestone. It does not add production model credentials, real external connectors, voice/vision, computer control, agents or autonomous workflows.

## Canonical conversation lifecycle

1. authenticated Root Owner or otherwise permitted actor enters a request; 2. device/session/security-epoch state is verified; 3. operating mode is resolved; 4. a conversation/turn envelope is created; 5. prior conversation state allowed by retention policy is loaded; 6. context-source candidates are collected; 7. memory retrieval is owner/project scoped and provenance-aware; 8. data classifications and NEVER_STORE rules are applied; 9. purpose-limited context is minimized; 10. model capability requirements are resolved; 11. privacy preflight selects an eligible local/external provider or fails closed; 12. model request is generated through the Foundation model port; 13. model output is treated as untrusted proposal/content, never authority; 14. any tool request becomes a tool proposal; 15. schema validation, policy and risk evaluation occur; 16. approval is requested when required; 17. exact approval/permit binding occurs; 18. governed execution occurs through the Universal Tool Gateway; 19. tool result is correlated back into the turn; 20. response generation continues; 21. stream events are emitted to the client; 22. permitted conversation state is persisted; 23. memory candidates are proposed but not silently promoted beyond memory policy; 24. audit/events are correlated without protected plaintext leakage; 25. retention/expiry/deletion rules remain enforceable; 26. cancellation, revocation, FREEZE, SAFE MODE or SHUTDOWN can terminate or restrict the flow at any point.

## J1 milestone decomposition

### J1.1 Conversation/session engine
Conversation creation, participant ownership, Foundation session binding, turn sequencing, idempotency and lifecycle state.

### J1.2 Context assembly engine
Deterministic context envelopes, source provenance, token/size budgets, owner/project scoping, freshness and classification filters.

### J1.3 Model orchestration runtime
Capability-based model routing through J0.6, provider-neutral request/response semantics, bounded timeouts, fallback rules that never weaken privacy.

### J1.4 Response generation and turn pipeline
Turn state machine from accepted input to completed/failed/cancelled response with explicit intermediate states.

### J1.5 Conversation persistence/history
Encrypted conversation/message persistence using Foundation storage semantics, retention, deletion, export and NEVER_STORE behavior.

### J1.6 Memory-aware conversation
Read-only retrieval integration first, followed by governed memory-candidate writes. Conversation text is not automatically long-term memory.

### J1.7 Tool-aware conversation
Model-suggested tools remain proposals. Execution occurs only via J0.7 gateway with schema, policy/risk, approval and exact permit binding.

### J1.8 Permission/approval-aware interaction
Natural-language approval prompts and resumable turns without changing Foundation authority semantics.

### J1.9 Operating modes and behavioral control
Assistant, Copilot, Autonomous, Focus, Private, Guest, Safe and Emergency modes affect eligible capabilities but cannot increase authority beyond policy.

### J1.10 Streaming/cancellation/resilience
Ordered stream events, reconnect/resume semantics, cancellation, model/provider failure, retry safety and no duplicate protected side effects.

### J1.11 Conversational Web UI
Authenticated web chat surface, stream rendering, approval UI, tool/result visibility, privacy/source indicators and emergency-state UX.

### J1.12 Full integration/adversarial validation
Exact-SHA, real-stack end-to-end qualification across identity → conversation → context → model → tool → audit/event → persistence → outage/recovery → shutdown.

## Non-negotiable security boundaries

- Conversation never creates authority.
- Model output is data, not authorization.
- Context disclosure is classification-aware and minimized before leaving JARVIS.
- D5 never reaches external model providers.
- NEVER_STORE remains non-durable at the conversation layer.
- Tool proposal and execution are distinct states.
- Partial/streaming output cannot commit protected actions.
- Retries cannot duplicate protected side effects.
- Revocation and security-epoch changes invalidate stale continuations.
- Emergency controls override ongoing turns and autonomy.
- Conversation history cannot resurrect deleted/expired memory.
- Audit correlation must not leak protected plaintext.

## J1.0 acceptance gates A–T

A released Foundation baseline is exact and immutable; B J1.0 scope/exclusions frozen; C conversation contract families versioned; D canonical lifecycle frozen; E identity/session/device/security-epoch boundary preserved; F conversation and message ownership/isolation defined; G context envelope/provenance/minimization defined; H memory boundary preserves J0.5 retention/NEVER_STORE semantics; I model routing preserves J0.6 provider neutrality/privacy; J tool proposal/execution separation preserves J0.7; K policy/risk/approval/permit semantics preserved; L operating modes/emergency override semantics defined; M persistence/retention/deletion/export rules defined; N streaming/cancellation/retry semantics defined; O audit/event correlation defined; P outage/degraded/recovery behavior defined; Q web UI security/approval contract defined; R milestone J1.1–J1.12 boundaries frozen; S release-metadata inconsistency is explicitly recorded and cannot override signed release evidence; T no J1 runtime implementation, migration or production credential is introduced by J1.0.

## J1.0 exit criteria

J1.0 is complete only when the architecture, contracts, security review, manifest and machine-readable A–T acceptance catalogue are committed on the isolated branch, all existing Foundation tests remain unchanged/passing, no migration is added, and the J1.0 acceptance test passes. J1.1 must not begin until J1.0 receives a separate Development GO decision.
