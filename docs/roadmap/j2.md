# J2 — Memory + Knowledge Graph

Status: ARCHITECTURE PLANNING

Protected J1 release baseline: `f75ed2d2d712fe32e64eb161a7ecab73dcb34db1`

Authoritative prior-stage closeout: `docs/roadmap/j1-release-closeout.md`

## Objective

Build JARVIS Memory + Knowledge Graph as the next generation on top of the frozen J0/J1 system, without duplicating J0 storage/security/memory contracts or J1.6 memory-aware conversation coordination.

J2 turns memory from a governed conversational capability into a durable, inspectable, relational knowledge system that can support future projects, research, agents, multimodal interaction, proactive events and world-model reasoning.

The defining rule remains:

**JARVIS is the system. Models are replaceable brains. Memory and knowledge remain owner-controlled JARVIS state.**

## Existing capabilities J2 must reuse

J2 starts from already-completed foundations, including:

- J0 owner/security/privacy/retention/audit boundaries;
- PostgreSQL/pgvector storage infrastructure;
- J1 conversation/session binding;
- J1 context assembly;
- J1 durable conversation/history persistence;
- J1.6 governed memory-aware conversation retrieval;
- classification/provenance/retention rules;
- NEVER_STORE and protected-data handling;
- operating-mode, approval and emergency controls;
- exact owner/project/conversation/session/security-epoch scoping.

J2 must not create a second memory authority, second privacy system, second vector store contract, second identity scope, or direct model-owned memory database.

## J2 architecture goals

J2 should establish five coordinated layers:

1. **Memory Registry** — canonical identity, type, scope, ownership, provenance, classification, retention, confidence and lifecycle metadata for every durable memory object.
2. **Memory Stores** — governed relational/vector/document/event persistence under existing storage authority.
3. **Knowledge Graph** — typed entities and relationships with provenance, confidence, temporal validity and source lineage.
4. **Memory Intelligence** — extraction, normalization, deduplication, consolidation, contradiction handling, ranking and retrieval planning; model outputs remain proposals until governed persistence rules accept them.
5. **Owner Controls** — inspect, search, correct, pin, forget, export, delete, retention controls and audit visibility.

## Canonical memory families

J2 must support the memory families frozen in the Master Definition:

- Working memory
- Conversation memory
- Personal memory
- Project memory
- Semantic memory
- Episodic memory
- Procedural memory
- Relationship memory
- Device memory

These are logical memory classes, not permission shortcuts. Each memory still obeys owner/project scope, classification, provenance, retention and deletion rules.

## J2 milestone plan

### J2.0 — Memory + Knowledge Architecture Freeze

Define canonical memory object, entity, edge, provenance, confidence, temporal validity, classification, retention, deletion and audit contracts. Map all J0/J1 inherited authority boundaries before runtime work begins.

Exit: architecture frozen; no duplicate authority; explicit J2 qualification strategy defined.

### J2.1 — Canonical Memory Registry

Implement canonical durable memory identity and lifecycle metadata. Support owner/project scope, memory family, source, classification, retention class, confidence, timestamps, supersession, deletion state and audit correlation.

Exit: deterministic registry contracts and storage migrations pass focused tests.

### J2.2 — Governed Memory Ingestion

Create ingestion pipelines from conversation/history, explicit owner saves, project artifacts and approved system events. Extraction/model output is untrusted proposal data until validated against policy, scope, classification and retention.

Exit: no cross-scope ingestion; NEVER_STORE cannot become durable; provenance required.

### J2.3 — Memory Normalization, Deduplication + Consolidation

Normalize equivalent memories, detect duplicates, merge compatible evidence, preserve conflicting evidence, and maintain source lineage rather than overwriting history silently.

Exit: deterministic duplicate/consolidation behavior; conflicts remain inspectable.

### J2.4 — Semantic Retrieval + Ranking v2

Extend the frozen J1.6 retrieval interface with hybrid lexical/vector/metadata/graph-aware candidate selection while preserving J1 context-budget and privacy boundaries.

Exit: retrieval quality improves without widening authority or context disclosure.

### J2.5 — Knowledge Graph Core

Implement entity/edge storage, typed schemas, provenance, temporal validity, confidence and source lineage. Graph updates must be idempotent and reversible where supported.

Exit: entity and relationship CRUD through governed internal APIs; no model-direct graph mutation.

### J2.6 — Entity Resolution + Identity Linking

Resolve duplicate entities carefully across names, emails, projects, devices, companies and aliases. Sensitive identity merges require stronger confidence and/or owner review according to policy.

Exit: false merges fail safe; every merge/split is auditable.

### J2.7 — Contradiction, Supersession + Temporal Truth

Represent facts that change over time, conflicting sources, corrected facts, superseded decisions and uncertain knowledge. Do not collapse uncertainty into false certainty.

Exit: current-state queries can distinguish active, historical, disputed and superseded facts.

### J2.8 — Project Memory System

Build rich project memory over repositories, architecture decisions, deployments, bugs, roadmaps, tasks, discussions and evidence. Connect project memory to the knowledge graph and existing conversation/project scope.

Exit: JARVIS can reconstruct project context without relying on one chat transcript.

### J2.9 — Personal, Procedural, Relationship + Device Memory

Implement governed long-term preference/procedure/contact/device memory with explicit owner controls and stronger handling for sensitive data.

Exit: owner can inspect/correct/delete these memories; no unauthorized cross-person leakage.

### J2.10 — Memory Lifecycle + Forgetting

Implement retention expiry, owner deletion, graph cleanup/tombstones where required, embedding/index removal, backup/recovery semantics and deletion propagation evidence.

Exit: forgetting is real, testable and does not resurrect deleted memories after restart/recovery.

### J2.11 — Memory/Graph Owner Console + APIs

Provide authenticated inspection/search/edit/correction/export/delete interfaces without moving authority into the UI. Show provenance, confidence, classification, relationships, history and retention state.

Exit: browser cannot inject owner/scope authority; all mutations pass trusted server boundaries.

### J2.12 — Final Memory + Knowledge Graph Integration Qualification

Run the complete J2 real-stack qualification against one frozen exact candidate, including inherited J0/J1 regressions, PostgreSQL/pgvector, graph lifecycle, retrieval, contradiction, deletion, backup/recovery, outage/restart, browser owner controls and adversarial scope/privacy tests.

Exit: exact candidate green -> non-force fast-forward -> exact-main qualification green -> **J2 Memory + Knowledge Graph v1 GO**.

## Required cross-cutting invariants

- J0/J1 authority remains frozen and authoritative.
- No model can silently persist a memory merely because it generated it.
- No model/provider owns canonical memory or graph state.
- All durable memories have provenance.
- All graph claims have provenance/source lineage.
- Scope is exact and fail-closed.
- Classification and retention are enforced at storage and retrieval boundaries.
- NEVER_STORE never enters durable memory, vector indexes, graph storage or backups.
- D5/protected content does not enter generic model context.
- Deletion/forgetting propagates through relational, vector and graph indexes.
- Retrieval does not become a permission bypass.
- Contradictory evidence remains representable.
- Confidence is not treated as authorization.
- Graph relationships cannot manufacture access rights.
- Owner corrections are preserved with audit history rather than silently rewriting evidence.
- Backup/recovery cannot resurrect deleted or expired data.
- Cross-owner/project leakage must be adversarially tested.

## Qualification strategy

Development uses focused/cheap checks first. Full inherited real-stack qualification is reserved for frozen exact candidates.

Each J2 milestone must define explicit acceptance gates proportional to the authority it touches. J2.12 must execute the consolidated release qualification, including inherited J0 + J1 Core + Conversation v1 regression.

Tests must never be weakened, skipped, reordered or bypassed merely to obtain green CI.

## Boundary with later generations

J2 does not implement:

- J3 voice/vision/multimodal interaction;
- J4 computer/browser/file control expansion;
- J5 project/coding/research agent capabilities beyond memory representation;
- J6 multi-agent orchestration;
- J7 productivity integrations;
- J8 proactive event intelligence;
- J9 advanced autonomy/simulation;
- J10+ device/world/local-AI/robotics generations.

J2 may expose stable memory/graph contracts those generations can consume later.

## Immediate next authorized step

Begin **J2.0 — Memory + Knowledge Architecture Freeze** from the frozen J1 release baseline. Do not start J2.1 implementation until J2.0 architecture, inherited authority map and acceptance/qualification plan are reviewed and frozen.
